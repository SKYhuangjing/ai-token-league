# T01 Protocol Probe Evidence

Probed: 2026-05-19

## 1. Deep Login — `GET https://api2.cursor.sh/auth/poll`

### Request

```
GET https://api2.cursor.sh/auth/poll?uuid=<uuid>&verifier=<codeVerifier>
```

| Param | Type | Description |
|---|---|---|
| `uuid` | string (36) | Random UUID generated by client |
| `verifier` | string (43) | PKCE code verifier, base64url-encoded |

### Browser URL

```
https://cursor.com/loginDeepControl?uuid=<uuid>&challenge=<challenge>&mode=login
```

| Param | Type | Description |
|---|---|---|
| `uuid` | string (36) | Same UUID used for poll |
| `challenge` | string (43) | `base64url(SHA256(codeVerifier))` |
| `mode` | string | `"login"` |

### Pending Response

| Field | Value |
|---|---|
| Status | `404` |
| Content-Type | `text/plain; charset=utf-8` |
| Body | `Not found` |

Poll interval: 2s. Pending until user completes browser login.

### Success Response

| Field | Value |
|---|---|
| Status | `200` |
| Content-Type | `application/json; charset=utf-8` |
| Content-Length | `1015` |

**Field names: `accessToken`, `refreshToken`, `challenge`, `authId`, `uuid`**

All fields are **camelCase**.

| Field | Type | Length | Prefix | Notes |
|---|---|---|---|---|
| `accessToken` | string | 413 | `eyJh...` | JWT |
| `refreshToken` | string | 413 | `eyJh...` | JWT |
| `challenge` | string | 43 | varies | Same challenge sent in browser URL |
| `authId` | string | 37 | `auth...` | Stable user identifier |
| `uuid` | string | 36 | varies | Same UUID from request |

**No `email` field in poll response.**

### JWT Payload (accessToken / refreshToken)

Both tokens share identical structure:

| Field | Type | Notes |
|---|---|---|
| `sub` | string | `auth0\|user_<id>`, same as `authId` from poll |
| `time` | number | Unix timestamp, issuance time |
| `randomness` | string | UUID fragment |
| `exp` | number | Unix timestamp, expiry (~60 days from issuance) |
| `iss` | string | `https://authentication.cursor.sh` |
| `scope` | string | Scopes |
| `aud` | string | `https://cursor.com` |
| `type` | string | `"session"` |

**No `email` in JWT payload.**

## 2. Token Refresh — `POST https://api2.cursor.sh/oauth/token`

### Request

```http
POST https://api2.cursor.sh/oauth/token
Content-Type: application/json

{
  "grant_type": "refresh_token",
  "client_id": "KbZUR41cY7W6zRSdpSUJ7I7mLYBKOCmB",
  "refresh_token": "<refreshToken from poll>"
}
```

**Request fields are snake_case.**

### Success Response

| Field | Value |
|---|---|
| Status | `200` |

**Field names: `access_token`, `id_token`, `shouldLogout`**

Response fields are **snake_case** (different from poll response).

| Field | Type | Length | Notes |
|---|---|---|---|
| `access_token` | string | 413 | New access token (JWT) |
| `id_token` | string | 413 | ID token (JWT, same structure as access_token, no email) |
| `shouldLogout` | boolean | — | `false` = token still valid |

### Key Findings

- **No `refresh_token` in response** — no rotation; must keep the original `refreshToken` from poll.
- `shouldLogout` field confirmed; `true` means refresh token invalidated, user must reauth.
- `id_token` JWT has same structure as access token (sub, time, randomness, exp, iss, scope, aud, type); **no email**.

## 3. Account Info — `GET https://cursor.com/api/auth/me`

### Request

```http
GET https://cursor.com/api/auth/me
Cookie: WorkosCursorSessionToken=<url_encoded_cookie>
```

Cookie format: `WorkosCursorSessionToken=` + `encodeURIComponent(jwtSub + "::" + accessToken)`

Where `jwtSub` is the `sub` field from accessToken JWT (e.g. `auth0|user_xxx`).

**Note**: This endpoint is on `cursor.com`, not `api2.cursor.sh`. Uses cookie auth, not Bearer token.

### Success Response

| Field | Value |
|---|---|
| Status | `200` |
| Content-Type | `application/json; charset=utf-8` |

**Field names: `email`, `email_verified`, `name`, `sub`, `created_at`, `updated_at`, `picture`, `id`**

| Field | Type | Sample (sanitized) | Notes |
|---|---|---|---|
| `email` | string | `j***@example.com` | Login email, usable as identity hash input |
| `email_verified` | boolean | `true` | |
| `name` | string | — | Display name |
| `sub` | string | `user_xxx` | WorkOS user ID (without `auth0\|` prefix) |
| `created_at` | string | ISO 8601 | |
| `updated_at` | string | ISO 8601 | |
| `picture` | string/null | — | Avatar URL |
| `id` | number | — | Numeric user ID |

## Summary: Protocol Shape Corrections vs Design Doc

| Design Doc Assumption | Actual Behavior | Impact |
|---|---|---|
| `access_token` (snake_case) in poll | `accessToken` (camelCase) in poll; `access_token` (snake_case) in refresh | Two different naming conventions; client must handle both |
| `refresh_token` (snake_case) in poll | `refreshToken` (camelCase) in poll | Field name correction |
| Poll response may contain email | No email in poll or JWT | Must call `cursor.com/api/auth/me` to get email |
| `api2.cursor.sh/auth/me` for account info | `cursor.com/api/auth/me` with cookie auth | Different host and auth method |
| `shouldLogout` in poll response | Only in refresh response | Correct scope: only relevant for refresh |
| `id_token` may contain email (OIDC standard) | No email in id_token JWT | Confirmed: must use `/api/auth/me` |
| Refresh returns new `refresh_token` (rotation) | **No `refresh_token` in refresh response** | No rotation; keep original `refreshToken` from poll |
| Access token expiry ~55min | JWT `exp` is ~60 days out | Long-lived; but scope/iss suggests server may invalidate earlier |
| `authId` field | Confirmed, matches JWT `sub` (with `auth0\|` prefix) | Stable account identifier, usable as fallback identity |
