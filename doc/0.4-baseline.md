# AI Token League 0.4 Baseline

Version: `0.4`
Drafted at: `2026-05-06`
Status: design baseline for initialization guide, first-run experience, diagnostics, and early admin data reset operations.

This baseline starts from `0.3-baseline.md`. The 0.4 implementation is versioned as `0.4.0`.

## 1. Product Goal

0.4 turns the first-run experience from a silent auto-initialization into an informed, consent-based setup that educates users about what the app does, what data is collected, and how to configure sources.

User-facing goals:

- New users understand what AI Token League does before any data collection begins.
- Users explicitly see the auto-generated cryptographic identity and understand its purpose.
- Users see which AI tools are already detected on their machine and can choose which to track.
- Users understand the privacy model: what is uploaded and what is never uploaded.
- Users can configure Cloud Connection or choose to remain local-only.
- Users can export a local diagnostics bundle for comparing client-side scan/sync facts with cloud data.
- CLI users get an interactive first-run experience instead of an error message.
- Admin users can reset one participant's uploaded server-side data during early data-correction windows, then let the same client re-register and re-upload fresh aggregate usage.
- Desktop users can opt into background silent updates so a verified client package is prepared automatically and applied without manual Finder/File Explorer replacement.

Non-goals:

- No account system.
- No change to the ranking truth: ranking remains `totalTokens`.
- No upload of prompts, assistant responses, source code, full transcripts, real absolute paths, Cursor session tokens, or identity private keys.
- No change to the provider scan/sync architecture.
- No change to the Settings tabs structure (Account / Sources / Cloud / Sync / App remains).
- No forced Cloud Connection; local-only mode remains fully functional for viewing local usage.
- Diagnostics export does not upload diagnostics automatically; it only writes a local JSON file selected by the user.
- Admin reset does not delete local client identity, local usage cache, upload queue files, source config, or any user machine data.
- Silent update does not bypass checksum verification, does not install non-zip packages, and does not modify identity, config, provider roots, Cursor tokens, aliases, usage cache, upload queue, or diagnostics files.

## 2. Initialization Guide Model

0.4 replaces the current `#onboarding-card` inline banner with a multi-step wizard overlay.

### 2.1 Desktop Wizard

The wizard is a full-screen modal overlay (`#wizard-overlay.modal-backdrop`) that blocks the entire app. The user must complete or skip the wizard before interacting with the main UI. The Today panel loads underneath the overlay so it is ready immediately when the wizard is dismissed.

Wizard steps:

| Step | Title | Purpose |
| --- | --- | --- |
| 1 | Welcome | Explain what the app does; show privacy disclosure. |
| 2 | Identity | Show auto-generated identity; nickname input; import full config. |
| 3 | Sources | Show auto-detected providers; toggle controls; manual add. |
| 4 | Cloud | Optional API base URL; explain cloud vs local-only. |
| 5 | Ready | Confirm choices; start tracking. |

Navigation rules:

- Each step has Back and Next buttons.
- Step 1 has no Back button.
- Step 5 has "Start tracking" instead of Next.
- A "Skip setup" link is available on every step; skipping uses defaults and dismisses the wizard.
- "Import existing config" on the Identity step loads a full config JSON file (including nickname, apiBaseUrl, provider settings, workdir aliases, etc.) and dismisses the wizard. Old profile-only files (containing just participantId, nickname, identityPublicKey, identityPrivateKey) are also accepted — missing fields use safe defaults.
- Progress indicator shows step numbers with current step highlighted.

Trigger condition:

- `desktopAutoInitialized === true` triggers the wizard.
- Completing or skipping the wizard sets `desktopAutoInitialized: false`.
- `isUnconfirmedDesktopProfile()` remains unchanged for detecting untouched configs.

### 2.2 CLI Interactive Init

When no config exists and no `--nickname` flag is provided, `npm run collector:init` enters interactive mode:

- Prompts for nickname.
- Shows detected sources.
- Prompts for optional API base URL.
- Prints configuration summary.

When `--nickname` or `--api` flags are provided, behavior is unchanged (non-interactive).

## 3. Privacy Disclosure Baseline

The onboarding must explicitly communicate what is and is not collected.

What IS collected:

- Daily aggregated token counts per tool, model, and workdir hash.
- Workdir display name (directory basename only, e.g. "my-project").
- Provider version and parser version (data lineage).
- Device ID and participant ID (anonymous, no personal info).

What is NEVER collected:

The following 14 fields are explicitly blocked from upload payloads (`FORBIDDEN_UPLOAD_FIELDS` in `schema.js`):

| Field | User-facing description |
| --- | --- |
| `prompt` | Your prompts are never collected. |
| `assistantResponse` | Assistant responses are never collected. |
| `content` | File content is never collected. |
| `sourceFileContent` | Source code is never collected. |
| `fullTranscript` | Full conversation transcripts are never collected. |
| `absolutePath` | Real file paths are never collected. |
| `localPath` | Local directory paths are never collected. |
| `identityPrivateKey` | Your signing key never leaves your machine. |
| `access_token` | Access tokens are never collected. |
| `refresh_token` | Refresh tokens are never collected. |
| `workosSessionToken` | Cursor session tokens stay on your computer. |
| `cursor_auth_raw` | Cursor authentication data is never collected. |
| `cursor_usage_raw` | Raw Cursor API responses are never collected. |
| `cookie` | Browser cookies are never collected. |

Privacy disclosure placement:

- Desktop: Welcome step shows a privacy callout box with human-readable statements.
- CLI: Interactive init shows a privacy summary before prompting.
- The existing rail sidebar text ("No prompts, responses, code, or real paths are uploaded") remains.

## 4. Source Auto-Detection Baseline

The wizard uses existing provider `detect()` methods to show what is found before enabling.

Detection results:

| Provider | Detection method | What it checks |
| --- | --- | --- |
| Claude Code | `providerHealth()` | `~/.config/claude/projects` and `~/.claude/projects` |
| Codex | `providerHealth()` | `$CODEX_HOME` and `~/.codex` |
| Cursor | `providerHealth()` | Local account sources via `discoverAccountSources()` |

Product rules:

- Auto-detection runs during the wizard but does not enable providers until the user confirms.
- Providers with `detected: true` are pre-enabled in the wizard UI; user can toggle off.
- Providers with `detected: false` are shown as "Not found" with an "Add location" option.
- Cursor is Off by default even if detected, because it requires a separate token.
- Toggling in the wizard does NOT trigger a scan; it only sets the config preference.

## 5. Cloud Connection Baseline

The wizard Step 4 explains what cloud sync enables and lets users configure or skip.

What cloud enables:

- Upload usage to the public community leaderboard.
- Check for client updates via app-server release config.
- Fetch model pricing data for estimated cost display.

Update apply rule:

- macOS and Windows zip updates are downloaded, checksum-verified, then installed by the app through a restart flow.
- The user does not need to open Finder or manually replace the app bundle after choosing the restart update action.
- Non-zip update packages remain a verified download handoff until a native apply path is implemented.

Background silent update rule:

- Silent update is a Desktop App setting, separate from Cloud Connection but only active when Cloud Connection is configured and reachable.
- The default mode is `notify`: the app checks in the background and tells the user when an update is available, but does not download or restart without user action.
- Users can switch to `auto_download`: the app checks, downloads, and checksum-verifies supported zip artifacts in the background, then marks the update as ready.
- Users can switch to `auto_apply_on_idle`: after a verified background download, the app installs and restarts automatically only when no foreground scan, sync, diagnostics export, settings import/export, or update apply is running.
- Mandatory updates may use `auto_apply_on_idle` even when the normal mode is `notify`, but still must wait for the same safe-idle guard.
- Silent update never runs in local-only mode because the app-server release config is the only update source.
- Failed silent download, checksum, or apply attempts leave the current app usable and write a runtime log event plus a visible Settings > App status.

What local-only means:

- All data stays on this device.
- User can still view local usage, token composition, and workdir breakdown.
- No update checks, no leaderboard participation, no pricing data.

Product rules:

- Cloud Connection is optional; the wizard always allows proceeding without it.
- "Skip cloud" is explicit, not just leaving the field empty.
- The API base URL is validated via the existing `checkApiConnection()` flow.
- The wizard does not expose OSS endpoint, bucket, prefix, or manifest URL.

## 6. Client Observability Baseline

0.4 adds a local diagnostics export for support and data reconciliation.

Purpose:

- Compare local `usage-cache` aggregate rows with cloud `usage_daily` rows.
- Inspect upload queue payloads when sync fails or is delayed.
- Reconstruct client runtime steps around scan, cache reuse, API health, sync success, and queued uploads.
- Diagnose mismatches without collecting prompts, responses, code, real paths, Cursor tokens, or identity private keys.

Runtime log:

- Desktop writes newline-delimited JSON events to Electron `userData/runtime-log.jsonl`.
- Events include app startup, config save, API health success/failure, scan start/done/cache-hit/failure, sync start/success/queued, background refresh start/done/failure, identity import/export, provider root add, Cursor token add, and diagnostics export.
- Runtime logs are bounded by size and rotated locally.
- Log details are sanitized before write; sensitive keys such as identity private key, Cursor token, cookie, and provider roots are redacted.

Diagnostics export:

- The entry point is in Settings > App, alongside version and runtime management actions.
- The export uses a save dialog and writes a local JSON file named `ai-token-league-diagnostics-<timestamp>.json`.
- The bundle includes app/client metadata, sanitized config, background status, usage cache rows, upload queue aggregate payloads, source index summaries, and recent runtime log events.
- The bundle does not include `identityPrivateKey`, Cursor session tokens, provider root real paths, prompts, responses, source code, full transcripts, or raw Cursor auth/usage payloads.
- Provider roots are represented only as per-provider counts.
- Upload queue payloads remain aggregate usage facts only, matching the existing privacy boundary.

## 8. Admin Data Reset Baseline

0.4 adds an early-stage admin operation for data correction when uploaded aggregate facts were produced by a buggy client, parser, or source rule.

Purpose:

- Remove one participant's server-side facts quickly during early statistics correction.
- Clear upload batch dedupe records so the same client can sync the same aggregate payload again.
- Keep the reset scoped to server-side aggregate data only.

Delete scope:

| Data area | Reset behavior |
| --- | --- |
| `participants` | Deletes the selected participant identity record from the server store. |
| `devices` | Deletes devices owned by that participant. |
| `workdirs` | Deletes workdir metadata owned by that participant. |
| `usage_daily` | Deletes all uploaded daily aggregate rows for that participant. |
| `upload_batches` | Deletes upload batch dedupe records for that participant. |
| `aggregateCache` | Invalidated after deletion. |

The active API route is:

```text
DELETE /api/admin/participants/:participantId
```

Admin UI behavior:

- `/admin.html` Usage ranking rows expose a `Reset user` action.
- The action requires browser confirmation before deletion.
- After deletion, Admin usage, pricing, and quality views refresh.
- If the deleted participant was selected in the filter, the filter resets to All users.
- The user must run client sync again; the normal `POST /api/devices/register` and `POST /api/usage/daily-batch` flow recreates server-side identity and aggregate rows.

MySQL behavior:

- MySQL deletion runs in one transaction.
- Rows are removed in foreign-key-safe order: upload batches, usage rows, workdirs, devices, participant.

## 9. Admin Model Price Alias Baseline

0.4 also adds an explicit admin-controlled model price alias for provider display models that do not directly match cached or custom pricing keys.

Problem:

- Cursor dashboard can report display models such as `Premium (Codex 5.3)`.
- The display model must remain unchanged in uploaded usage facts and UI breakdowns.
- The server should not silently infer provider-specific pricing keys from display names.
- Missing-price handling needs a fast path to map one display model to an existing priced model.

Product rules:

- Cursor `default`, `auto`, and empty model names are collected as display model `Auto`.
- Cursor `Premium (...)` model names are collected and displayed as-is.
- Pricing does not use hard-coded `Premium (...)` or `Codex x.y` conversion rules.
- Admin users map a missing model to an existing custom or OpenRouter priced model.
- After mapping, `usage_daily.model` remains the original display model and `usage_daily.pricingModel` records the mapped priced model.
- If the mapped target price is deleted, aliases pointing to that target are removed and costs are recalculated.

Storage:

| Store | Field/Table | Purpose |
| --- | --- | --- |
| JSON | `modelPriceAliases` | `{ sourceDisplayModel: targetPricingModel }` mapping. |
| MySQL | `model_price_aliases` | Durable mapping table with `model`, `targetModel`, and `updatedAt`. |

API:

```text
POST   /api/admin/model-price-aliases
DELETE /api/admin/model-price-aliases/:model
```

Admin UI behavior:

- `/admin.html` Model prices tab shows mapping controls inside `Missing price tasks`.
- Each missing model row can be mapped to an existing custom or OpenRouter priced model.
- Existing aliases are listed under `Model aliases` and can be deleted.
- Saving or deleting an alias recalculates costs and refreshes usage, pricing, and quality views.

## 11. Confirmed Decisions

| Decision | Default | Reason |
| --- | --- | --- |
| Identity creation | Automatic, shown in wizard | Avoids friction; user sees the identity but doesn't manually generate it |
| Wizard skippable | Yes, via "Skip setup" link | Users who know the app can skip; defaults are safe |
| Cloud optional | Yes, "Skip cloud" button | Local-only mode is valid; no forced server dependency |
| Wizard replaces onboarding-card | Yes, card HTML removed | Avoids two competing first-run UIs |
| CLI interactive mode | Only when no config and no flags | Preserves existing script usage; adds guided path for new users |
| Privacy disclosure | Welcome step + CLI init | Converts FORBIDDEN_UPLOAD_FIELDS to user-facing language |
| Source pre-enable | Detected sources pre-enabled | Reduces wizard steps; user can toggle off |
| Cursor default Off | Even if detected | Requires separate token; pre-enabling would confuse users |
| Diagnostics location | Settings > App | Diagnostics is client runtime support, not only sync configuration |
| Diagnostics format | Local JSON file | Easy to attach to support/debug workflows and compare with cloud facts |
| Runtime log scope | Aggregate operational events only | Supports troubleshooting without expanding upload privacy surface |
| Admin reset scope | One participant's server-side aggregate data | Fixes early bad statistics without touching local client data |
| Upload batch reset | Delete participant upload batches with usage rows | Allows the same corrected or rescanned client payload to be accepted again |
| Wizard modal | Full-screen overlay blocking main app | User must complete or skip before accessing the app; Today panel preloads underneath |
| Config export/import | Full config (not just identity) | Includes apiBaseUrl, provider settings, workdir aliases, display preferences; old profile-only files remain compatible |
| Model price alias | Explicit Admin mapping | Avoids hidden pricing guesses while giving Missing Price a fast remediation path |
| Cursor Auto display | `Auto` | Keeps Cursor dashboard display style aligned with `Premium` without changing pricing semantics |
| Silent update default | `notify` | Background checks are useful, but silent restart needs an explicit user mode or mandatory update |
| Silent update source | app-server release config only | Keeps sync, pricing, compatibility, and update source-of-truth aligned |
| Silent apply boundary | zip artifacts only | Zip package semantics match the restart updater; native installers remain verified handoff |
