## 1. Baseline State

## 2. Scope

### 2.1 Legacy Update System Cleanup

**Problem**: 0.5.1 引入 electron-updater 后曾计划清理旧版自定义更新系统；但 0.5.2 已确认 macOS 在无 Developer ID 前仍需要自研 zip updater，继续依赖 `latest.json`、`/api/release/latest`、`buildReleaseManifest()`、`validateReleaseManifest()`、`selectUpdateArtifact()` 和 `updateStateFromManifest()`。

**Deferred Goal**: 在所有活跃客户端迁移出 macOS zip updater 后，再清理旧版更新系统遗留代码，并统一到不依赖 `latest.json` 的更新机制。

**Boundary**:

- 当前版本不删除 macOS zip updater 依赖
- 保留 `/api/release/latest` 和 `latest.json`
- 保留 `buildReleaseManifest()`、`validateReleaseManifest()`、`selectUpdateArtifact()`、`updateStateFromManifest()` 等 macOS zip updater 所需函数
- Web 前端下载面板已迁移到 `/api/release/config` 的 `release.installers`
- 后续清理前提：所有活跃客户端已迁移到不依赖 `latest.json` 的更新路径

**Privacy / Storage / API impact**:

- Privacy: 无新数据采集
- Storage: 无新表或文件
- API: `/api/release/config` 不暴露 `manifestUrl`；`/api/release/latest` 保留给 macOS zip updater

**Status**: DEFERRED — 0.5.2 restored `/api/release/latest` and `latest.json` for macOS zip updater dual-path support; cleanup blocked until all active clients migrate to electron-only update path.

### 2.2 Build-time Preset Configuration

**Problem**: 桌面客户端的默认值（`apiBaseUrl`、`autoRefreshEnabled`、`refreshIntervalMinutes` 等）全部硬编码在 `initConfig()` 中。部署时需要用户手动配置云端地址、开启自动同步等，初始化引导成本高。无法像渠道分发一样，在打包阶段预置一套默认配置。

**Goal**: 提供构建时预置配置能力，打包阶段注入一个 `preset.json`，桌面客户端首次启动时用预置值替代硬编码默认值。仅首次启动生效，用户修改后以用户配置为准。

**Boundary**:

- 新增 `scripts/build-preset.js`：从环境变量读取预置值，生成 `assets/preset.json`
- 新增 `src/shared/preset.js`：运行时加载预置配置的纯函数模块
- 修改 `src/desktop/main.cjs`：在 `ensureDesktopConfig()` 中合并预置值到 `initConfig()`
- 预置字段白名单：`apiBaseUrl`、`nickname`、`language`、`autoRefreshEnabled`、`refreshIntervalMinutes`、`silentUpdateMode`、`launchAtLogin`、`showEstimatedCost`、`showRawTokens`、`providerEnabled`
- Provider 配置：支持 `PRESET_PROVIDER_<ID>=true/false` 环境变量，可用 provider ID：`claude_code_local`、`codex_local`、`cursor_dashboard_usage`
- 语言配置：`language` 字段移入 config.json，与 localStorage 双向同步；支持 `PRESET_LANGUAGE` 环境变量
- 移除未使用的 `publicUpload` 字段
- 禁止预置字段（必须运行时生成）：`participantId`、`identityPublicKey`、`identityPrivateKey`、`deviceId`、`createdAt`、`desktopAutoInitialized`
- 环境变量前缀 `PRESET_*`，写入 `env.example`
- `assets/preset.json` 加入 `.gitignore`（构建产物，不提交）
- `npm run preset` 链入 `release:build`，确保每次构建从环境变量重新生成
- 无环境变量时生成空对象 `{}`，不影响默认行为

**Privacy / Storage / API impact**:

- Privacy: 无新数据采集
- Storage: 首次启动时预置值写入 `~/.ai-token-league/config.json`
- API: 无新或变更端点

**Status**: DONE

### 2.3 Installer Download Fallback

**Problem**: 热更新流程失败时（网络中断、文件损坏、权限不足等），客户端仅显示错误信息，用户无自救路径。发布脚本已将安装包（macOS DMG / Windows EXE）上传至 OSS，但客户端缺乏下载和引导安装的能力。Web 前端也需要从 `/api/release/config` 的 `release.installers` 读取安装包信息，避免继续把 public 下载入口绑定到 zip updater manifest。

**Goal**: 热更新失败时，桌面客户端提供「下载安装包」作为兜底方案；web 前端下载面板迁移到 `/api/release/config` 数据源。

**Design**:

*数据源统一*：发布脚本（`publish-release.js`）在发布时生成 `installer.json`（含各平台 url/sha256/size/ext），上传到 OSS 的 `{prefix}/releases/installer.json`。服务端 `/api/release/config` 读取该文件，填入 `release.installers` 字段返回。客户端和 web 前端直接读取，无需运行时推导。

*桌面端触发条件*：`autoUpdater` 触发 `error` 事件，即热更新检查或下载失败时，在 UI 上展示「下载安装包」入口。无需自动触发，由用户主动点击。

*桌面端下载与安装流程*：
1. 用户点击「下载安装包」→ 主进程通过 `session.downloadURL()` 发起下载
2. 下载进度通过 IPC 实时推送到渲染进程，展示百分比和速度
3. 下载完成后校验 SHA-256，不匹配则拒绝打开并提示用户
4. 校验通过后主进程通过 `shell.openPath()` 打开安装包：
   - macOS：打开 DMG，提示用户拖拽到 Applications
   - Windows：启动 EXE 安装向导
5. 安装包下载到系统临时目录，安装完成后由 OS 自行清理

*平台差异*：

| 平台 | 安装包格式 | 打开方式 | 用户操作 |
| --- | --- | --- | --- |
| macOS (arm64/x64) | `.dmg` | `shell.openPath()` 挂载 DMG | 拖拽 .app 到 Applications 文件夹 |
| Windows (x64) | `.exe` | `shell.openPath()` 启动安装向导 | 按向导提示完成安装 |

**Boundary**:

- 修改 `scripts/publish-release.js`：发布时生成 `installer.json` 并上传到 `{prefix}/releases/installer.json`
- 修改 `src/backend/server.js`：
  - `/api/release/config` 响应新增 `release.installers` 字段，从 OSS 读取 `installer.json` 透传
  - 保留 `/api/release/latest` 端点路由，供 macOS zip updater 使用
- 修改 `src/desktop/main.cjs`：
  - 新增 `ipcMain.handle("update:download-installer")` 处理安装包下载
  - 下载使用 `session.downloadURL()`，进度通过 `update:installer-progress` IPC 推送
  - 下载完成后校验 SHA-256，通过后 `shell.openPath()` 打开安装包
- 修改 `src/desktop/preload.cjs`：暴露 `downloadInstaller` 和 `onInstallerProgress` API
- 修改 `src/desktop/renderer.js`：热更新失败时展示「下载安装包」按钮，下载中展示进度
- 修改 `src/desktop/index.html`：添加 `#download-installer` 按钮
- 修改 `src/web/app.js`：`loadReleaseDownloads()` 改为调用 `/api/release/config`，从 `release.installers` 读取下载地址
- 修改 `src/shared/i18n.js`：添加 `desktop.app.downloadInstaller` 中英文翻译

**Privacy / Storage / API impact**:

- Privacy: 无新数据采集
- Storage: 安装包临时下载到系统临时目录
- API: `/api/release/config` 响应新增 `release.installers` 字段（从 OSS `installer.json` 透传）；`/api/release/latest` 保留

**Status**: PARTIAL — installer.json 生成、服务端透传、桌面端 IPC 下载、web 下载面板已实现；`/api/release/latest` 端点保留（0.5.2 dual-path 需要），删除待客户端迁移后执行。

### 2.4 Authenticated Community Leaderboard and Public Landing Page

**Problem**: 当前 `/` 是公开社区榜单，并直接展示 token 排名、参与者、模型 breakdown 和下载面板。客户反馈公开榜单可能刺激用户刷 token；但客户端下载入口仍需要面向未登录访问者公开，否则新用户无法获取客户端。

**Goal**: 将社区榜单从公开页面改为可鉴权页面，鉴权能力复用 BasicAuth 机制但使用独立配置；同时把首页改为公开下载页。公开入口只保留版本信息、支持平台、功能特性和下载动作，不暴露排名、参与者或 token 数据。

**Source of truth checked**:

- `src/backend/server.js` 当前只对 `/admin.html` 和 `/api/admin/*` 调用 `checkBasicAuth()`
- `src/web/index.html` 当前同时承载公开榜单、参与者详情、语言切换和 `#download-panel`（已重命名为 `leaderboard.html`）
- `src/web/app.js` 当前从 `/api/public-leaderboard`、`/api/participants/:id`、`/api/participants/:id/trend` 拉取榜单与详情，并从 `/api/release/config` 渲染下载面板（已重命名为 `leaderboard.js`）
- `/api/release/config` 当前不依赖榜单数据，可作为公开首页的数据源

**Recommended design**:

1. Auth boundary
   - 新增 `PUBLIC_BOARD_AUTH_USERNAME` / `PUBLIC_BOARD_AUTH_PASSWORD` 可选配置。
   - 榜单鉴权与 admin 鉴权必须独立判定：`ADMIN_USERNAME` 只保护 admin；`PUBLIC_BOARD_AUTH_USERNAME` 只保护社区榜单。
   - 未配置 `PUBLIC_BOARD_AUTH_USERNAME` 时，社区榜单保持公开，即使 `ADMIN_USERNAME` 已配置。
   - 若客户希望榜单和 admin 使用同一账号，需显式把 `PUBLIC_BOARD_AUTH_USERNAME` / `PUBLIC_BOARD_AUTH_PASSWORD` 配成与 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 相同的值。
   - 榜单 API 统一迁移到 `/api/board/*` 命名空间，并在 `handleApi()` 入口像 `/api/admin/*` 一样统一鉴权。
   - 目标接口：`GET /api/board/leaderboard`、`GET /api/board/participants/:id`、`GET /api/board/participants/:id/trend`。
   - 鉴权保护范围必须包含 `/leaderboard.html` 和 `/api/board/*`。
   - 不保留旧榜单 API 兼容别名：`/api/public-leaderboard`、`/api/participants/:id`、`/api/participants/:id/trend` 在 0.6 中返回 `404`。
   - `/api/devices/register`、`/api/usage/daily-batch`、`/api/health`、`/api/release/config`、`/api/release/latest` 不进入该鉴权边界，避免影响客户端注册、同步、健康检查和更新。

2. Public landing page and leaderboard separation
   - `/` 为公开首页（下载页），无需鉴权，复用 `/api/release/config` 的 `latestClientVersion` 与 `release.installers`。
   - 首页展示产品名、简介、版本信息、功能特性（本地优先、多来源支持、社区排行榜）、下载按钮、榜单入口链接和语言切换。
   - 榜单页迁移到 `/leaderboard.html`，受 board auth 保护。
   - 首页不得展示社区排名、参与者昵称、token 总量、模型 breakdown、预估成本或 participant detail。
   - 榜单页保留榜单指标说明、周期筛选、成本开关、榜单和详情抽屉。

3. Navigation and rollout
   - 公开入口为 `/`，榜单入口为 `/leaderboard.html`。
   - 首页提供跳转到 `/leaderboard.html` 的链接，需鉴权后方可访问。
   - 外部传播下载链接指向 `/`。

4. Security and privacy boundary
   - 这是访问控制改造，不改变 token 排名口径、上传签名、存储模型或客户端身份模型。
   - 服务端仍只接收聚合 daily usage facts；不新增 prompt、assistant response、source code、真实绝对路径、Cursor session token 或 identity private key。
   - BasicAuth 只降低公开可见性，不解决恶意客户端伪造上传；刷 token 的根因仍需后续通过反作弊规则、异常检测或邀请制身份治理单独设计。

**Rejected alternatives**:

- 只隐藏页面下载块、不保护榜单 API：页面不可见但 API 仍公开，不能解决公开排名刺激和数据暴露问题。
- 沿用分散的 `/api/public-leaderboard` 与 `/api/participants/*` 路由：需要逐条维护鉴权规则，容易遗漏新榜单接口；当前无兼容要求，统一到 `/api/board/*` 更短。
- 直接把下载入口放进 admin：新用户无法公开下载客户端，传播成本上升。
- 用 admin 页面替代社区榜单：admin 展示运维字段和重置操作，权限与信息密度都不适合普通榜单查看者。
- 改 ranking truth 或减少 token 显示精度：会改变产品核心口径，且不能解决公开访问边界。

**Privacy / Storage / API impact**:

- Privacy: 榜单、参与者详情和 token 数据从公开可见变为受 BasicAuth 保护；公开下载页不暴露使用量数据。
- Storage: 无新表或文件存储；仅新增可选环境变量。
- API: 新增 `/api/board/*` 榜单命名空间并统一鉴权；旧的 `/api/public-leaderboard`、`/api/participants/:id`、`/api/participants/:id/trend` 不保留兼容；`/api/release/config` 保持公开。
- Web: `/` 为公开首页（下载页）；榜单页迁移到 `/leaderboard.html`（受鉴权保护）；`/index.html` 返回 404。

**Status**: DONE — binary board BasicAuth has been implemented; §2.6 supersedes its behavior model before the next implementation slice.

### 2.5 Public Landing Page Widescreen Optimization

**Problem**: 当前公开首页在 PC 宽屏中使用窄栏纵向布局，左右留白过大；下载卡片占据首屏核心空间，用户需要滚动才能看到「查看社区排行榜」入口。页面没有在首屏展示社区活跃度，导致排行榜产品的核心价值弱于下载动作。

**Goal**: 将公开首页改为上下结构：顶部品牌区，中上社区聚合预览，中下下载区，底部功能特性。PC 宽屏首屏应同时看到产品名、社区聚合预览、排行榜入口和三平台下载卡。

**Recommended design**:

1. Page structure
   - 顶部：产品名、短 tagline、语言切换。
   - 中上：社区排行榜预览模块，展示当前参与人数、今日总 token、本周总 token，并提供「查看社区排行榜」入口。
   - 中下：下载桌面客户端模块，展示 macOS arm64、macOS Intel、Windows 三个平台下载卡。
   - 底部：功能特性横向展示，包含本地优先、多来源支持、隐私聚合、社区排行。

2. CTA placement
   - 不保留左侧双主按钮；如果社区预览和下载模块已经各自承载具体动作，额外并列 CTA 会重复。
   - 「查看社区排行榜」只放在社区预览模块内。
   - 下载按钮只放在下载模块内。

3. Widescreen layout
   - 首页容器不再使用 `max-width: 720px` 的窄栏约束。
   - PC 宽屏使用更宽的内容区域，使预览卡和下载卡充分利用横向空间。
   - 移动端保持单列布局，下载卡回退为纵向排列。

4. Public aggregate data boundary
   - 公开首页只允许展示聚合指标：参与人数、今日总 token、本周总 token。
   - 公开首页仍不得展示社区排名、参与者昵称、模型 breakdown、预估成本或 participant detail。
   - 因 0.6 §2.4 已将 `/api/board/*` 置于可选 BasicAuth 边界内，公开首页不能依赖受鉴权的榜单 API 渲染预览。
   - 若确认公开聚合指标可展示，应新增公开聚合数据来源，例如 `GET /api/board/summary` 或等价端点；该端点必须只返回汇总数，不返回参与者列表、昵称、模型、来源或明细。

**Key files**:

- `src/web/download.html`
- `src/web/download.js`
- `src/web/styles.css`
- `src/backend/server.js`（仅当新增公开聚合端点时）
- `src/shared/i18n.js`
- `tests/`

**Privacy / Storage / API impact**:

- Privacy: 从“公开首页不暴露 token 数据”调整为“公开首页可展示有限聚合 token 数据”；不暴露排名、昵称、模型、来源或明细。
- Storage: 无新表或文件。
- API: 若当前接口无法在公开首页安全取数，需要新增公开聚合端点；不得复用受鉴权的 `/api/board/leaderboard` 作为公开首页数据源。
- Web: `/` 改为宽屏优先的信息架构；`/leaderboard.html` 仍是完整榜单页并受 board auth 保护。

**Status**: REVIEW — requires product confirmation because it changes the public data boundary defined in §2.4.

### 2.6 Board Security Levels and API-side Anonymization

**Problem**: §2.4 使用 `PUBLIC_BOARD_AUTH_USERNAME` 是否配置来决定榜单是否鉴权，控制粒度过粗。真实产品诉求有三档：默认全公开、公开但用户信息匿名化、完整榜单需要鉴权。匿名化不能只在前端隐藏昵称，因为 API 仍会泄露真实 `participantId`、nickname 和可关联详情。

**Goal**: 将榜单访问控制从“是否配置 BasicAuth 凭据”升级为明确的安全级别。默认全公开；中间档为 API 数据级匿名化；最高档为 BasicAuth 鉴权。匿名化后的身份要稳定、不可反推、可点击查看详情，并且展示名称要有趣，不是冷冰冰的 `User 123`。

**Recommended design**:

1. Security level
   - 新增 `BOARD_SECURITY_LEVEL=public | anonymous | authenticated`。
   - 默认值为 `public`，保持当前公开榜单体验。
   - `PUBLIC_BOARD_AUTH_USERNAME` / `PUBLIC_BOARD_AUTH_PASSWORD` 只作为 `authenticated` 模式的凭据，不再隐式决定榜单是否鉴权。
   - 若 `BOARD_SECURITY_LEVEL=authenticated` 但未配置 board 凭据，服务端启动时报错并退出；配置错误必须尽早暴露，不能运行时降级公开。

2. Level behavior
   - `public`: `/leaderboard.html` 与 `/api/board/*` 无需鉴权；API 的规范身份字段为 `displayId = participantId`、`displayName = nickname`。
   - `anonymous`: `/leaderboard.html` 与 `/api/board/*` 无需鉴权；API 的规范身份字段为 `displayId = participantPublicId`、`displayName = 天文星体名`，不返回真实 nickname、真实 `participantId`、设备信息或任何可反查字段。
   - `authenticated`: `/leaderboard.html` 与 `/api/board/*` 需要 board BasicAuth；登录后 API 的规范身份字段为 `displayId = participantId`、`displayName = nickname`。
   - 前端只允许读取 `displayId` 和 `displayName`，不得根据 security level 分支读取 `participantId` / `nickname`。

3. API-side anonymization
   - 匿名化必须在 `src/backend/server.js` 的路由响应层完成（store 保持返回原始字段，server.js 做 `participantId` → `displayId`、`nickname` → `displayName` 的映射），前端只消费匿名后的字段。
   - `/api/board/leaderboard` 在所有模式下都返回 `displayId`、`displayName`、rank、token totals、模型 breakdown 等榜单展示字段。
   - `public` / `authenticated` 模式下 `displayId` 等于真实 participant id，`displayName` 等于真实 nickname；`anonymous` 模式下 `displayId` 等于匿名 public id，`displayName` 等于天文星体名。
   - `/api/board/participants/:id` 和 `/api/board/participants/:id/trend` 始终接受 `displayId`；`anonymous` 模式下服务端用反向 Map 映射到真实 participant，响应继续只返回匿名字段。
   - `avatarColor` 必须从当前响应的 `displayId` 派生；anonymous 模式不得继续使用真实 participant id 派生颜色。
   - anonymous 模式下不得返回 `workdirDisplayName`、真实 workdir、topWorkdir、设备信息或可关联到本地目录的字段；如详情仍需表达工作目录维度，只能返回泛化标签（如 `Workdir 1`）或省略该维度。
   - admin API 不受匿名化影响，仍返回真实运营数据。
   - `/api/board/summary` 若存在，只返回聚合数，不参与身份匿名逻辑。

4. Anonymous identity model
   - 在 `src/shared/crypto.js` 新增 `hmacSha256Hex(key, data)`，匿名化逻辑复用该工具；不要在 `server.js` 内联散落 HMAC 实现。
   - `participantPublicId = HMAC_SHA256(BOARD_ANONYMIZATION_SALT, participantId)` 的前 16 个 hex 字符。
   - `BOARD_ANONYMIZATION_SALT` 可选；未配置时服务端从独立 salt 文件读取，文件不存在则生成并写回。
   - 新增 `BOARD_ANONYMIZATION_SALT_PATH` 可选配置；默认路径为 `data/board-anonymization-salt.key`。该文件不写入 `db.json`，避免与业务数据耦合，便于运维备份和迁移。
   - 写入 salt 文件前需确保父目录存在（`fs.mkdirSync(dir, { recursive: true })`），首次部署时 `data/` 目录可能尚未创建。
   - 匿名名称由 public id 确定性生成，保证同一用户在同一部署中稳定展示。
   - 默认词库为 `assets/anonymizer-names.json`；可通过 `BOARD_ANONYMIZATION_NAMES_PATH` 指向自定义 JSON 词库文件（字符串数组）覆盖；未配置或文件非法时使用内置星体词库作为 fallback。
   - 名称去重：同一词库名词首次分配直接使用（如"火星"），之后重名自动加数字后缀（"火星 2"、"火星 3"）。已有用户的名称不会因新增用户而改变。
   - 不允许从用户 nickname 派生，避免泄露真实信息。

5. Reverse lookup cache
   - anonymous 模式需要 `participantPublicId -> participantId` 反向 Map，禁止在每次详情请求时逐个重算 HMAC 做 O(n) 扫描。
   - Map 在服务端启动时构建（与 salt 加载同生命周期）；之后详情查询为 O(1)。不延迟到首次请求，避免首请求延迟尖刺，且与 `authenticated` 缺凭据启动失败的设计理念一致。
   - 缓存失效时机：`BOARD_ANONYMIZATION_SALT` 或 salt 文件内容变化、participant 新增/删除、participant id 集合变化、服务端重启。
   - JSON store 可在 `registerDevice()` / `deleteParticipantData()` 后标记 board anonymizer cache dirty；MySQL store 可在读取 participant 列表版本变化或相关写操作后标记 dirty。

6. Detail and link behavior
   - 榜单行点击统一使用 `displayId` 构造详情请求。
   - URL、DOM dataset、raw data、title、error message 中都不得出现真实 `participantId` 或 nickname。
   - 如果 public id 无法映射到真实 participant，详情接口返回 `404`，不要泄露“真实用户不存在/已删除”等内部差异。

7. Configuration examples
   - 默认全公开：
     ```text
     BOARD_SECURITY_LEVEL=public
     ```
   - 公开匿名榜：
     ```text
     BOARD_SECURITY_LEVEL=anonymous
     BOARD_ANONYMIZATION_SALT=<server-secret>
     # Optional; defaults to data/board-anonymization-salt.key
     BOARD_ANONYMIZATION_SALT_PATH=data/board-anonymization-salt.key
     ```
   - 鉴权完整榜：
     ```text
     BOARD_SECURITY_LEVEL=authenticated
     PUBLIC_BOARD_AUTH_USERNAME=board
     PUBLIC_BOARD_AUTH_PASSWORD=secret
     ```

**Rejected alternatives**:

- 继续用 `PUBLIC_BOARD_AUTH_USERNAME` 是否存在作为行为开关：无法表达“配置了凭据但暂时公开”或“公开匿名”。
- 只在前端改昵称：API、链接、详情请求仍泄露真实身份，不满足匿名化目标。
- API 按模式返回不同身份字段：会把安全级别泄露到前端实现，增加发版和回归成本；统一 `displayId` / `displayName` 更稳定。
- 每次详情请求逐个重算 HMAC：实现短但查询复杂度为 O(n)，参与者增长后不可控；反向 Map 更适合这个读多写少场景。
- 每次请求都随机生成名称：有趣但不可追踪，用户无法在不同周期识别自己的排名变化。
- 直接隐藏详情抽屉：实现更短，但匿名 public id 足以支持详情，同时不牺牲榜单可玩性。

**Privacy / Storage / API impact**:

- Privacy: 新增匿名公开档，公开 API 不再暴露真实用户身份；token 排名和模型 breakdown 仍可公开展示。
- Storage: 需要持久化或配置 `BOARD_ANONYMIZATION_SALT`；默认独立文件 `data/board-anonymization-salt.key`；不新增业务表。
- API: `/api/board/*` 始终提供 `displayId`、`displayName`；anonymous 模式下移除 `participantId`、nickname、真实 workdir、设备信息，并从 `displayId` 派生 `avatarColor`。
- Web: `/leaderboard.html` 使用统一字段渲染显示名和详情链接，不能假设真实 participant id 或 nickname 永远存在。

**Status**: DONE — supersedes the binary board BasicAuth decision in §2.4. `displayId`/`displayName` unified across all modes; anonymous mode uses HMAC-based publicId and astronomical names; reverse map built at startup.

### Board Security Levels and API-side Anonymization

1. 默认未配置 `BOARD_SECURITY_LEVEL` 时等同 `public`
2. `BOARD_SECURITY_LEVEL=public`：
   - `/leaderboard.html` 返回 `200`
   - `/api/board/leaderboard` 返回 `200`
   - 响应包含 `displayId` 和 `displayName`
   - `displayId` 等于真实 participant id，`displayName` 等于真实 nickname
3. `BOARD_SECURITY_LEVEL=anonymous`：
   - `/leaderboard.html` 返回 `200`
   - `/api/board/leaderboard` 返回 `200`
   - 响应包含 `displayId` 和 `displayName`
   - 响应不包含真实 `participantId`、nickname、deviceId
   - 响应不包含 `workdirDisplayName`、真实 workdir、topWorkdir
   - `avatarColor` 从匿名 `displayId` 派生
   - 同一 participant 多次请求得到相同匿名 `displayId` 和 `displayName`；`displayName` 来自词库名词，重名时自动加数字后缀（如"火星 2"）
   - `/api/board/participants/:displayId` 和 `/trend` 可返回匿名详情，响应不泄露真实身份
   - 详情反查通过 `participantPublicId -> participantId` Map 完成，不做每次请求 O(n) HMAC 扫描
4. `BOARD_SECURITY_LEVEL=authenticated` 且未配置 board 凭据：
   - 服务端启动失败，不允许降级公开
5. `BOARD_SECURITY_LEVEL=authenticated` 且配置 `PUBLIC_BOARD_AUTH_USERNAME=board PUBLIC_BOARD_AUTH_PASSWORD=secret`：
   - 未带凭据访问 `/leaderboard.html` 和 `/api/board/leaderboard` 返回 `401`
   - 带 `board:secret` 访问返回 `200`
   - 响应包含 `displayId` 和 `displayName`
   - `displayId` 等于真实 participant id，`displayName` 等于真实 nickname
6. 未配置 `BOARD_ANONYMIZATION_SALT` 时，服务端创建或读取 `data/board-anonymization-salt.key`；首次部署时 `data/` 目录不存在也能正常写入

8. admin API 在三种 board security level 下都不做匿名化
