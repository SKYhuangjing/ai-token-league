# 算力共享 · 借用目录产品方案（规模化）

版本：v1.0（2026-09-19）· 状态：待评审
前置：车道模型（compute-sharing-lanes-design.md）已上线；R51 可靠性 + R52 接入体验已发布（卡 0.8.5 / dylib 0.3.1）。

---

## 1. 背景与问题

当前借用目录把所有在线分享节点平铺展示，无排序、无过滤、无借用方容量约束。验证期单节点运行良好；当在线节点增多（团队推广后预期 10-50 个）时：

1. 借用方需人眼扫描全部节点才能找到「可认领」的——发现成本随节点数线性增长。
2. 「值得认领」的信号（名额、剩余预算、开放状态）没有参与排序，全满节点与空闲节点视觉无差异。
3. 无借用方容量上限：一个人可以把所有节点的名额全部认领光（仅 6 次/分钟的频率限制），多节点时代是囤积漏洞。
4. 单节点多车道时目录纵向长度失控（50 节点 × 2-3 车道 ≈ 100+ 行）。

## 2. 目标与非目标

### 目标
- G1 借用方在 30 秒内找到「现在就能用、服务我要的模型」的车道并完成认领。
- G2 目录顺序天然把可用的排前面，不可用的折叠且不消失。
- G3 防囤积：任何借用方的并发有效认领有上限，超限有明确反馈。
- G4 目录在 100 节点 / 300 车道规模下渲染与滚动不劣化。

### 非目标（本期明确不做）
- 节点评分 / 推荐系统（等真实借用量数据，见 §10）。
- 分页或虚拟滚动（几百节点内客户端过滤足够）。
- 服务端过滤参数（数据量小，客户端实现即可，减少 API 版本分叉）。
- 跨节点负载均衡 / 自动切换。
- 中继与 TLS（运营侧约定，见整体评审记录）。

## 3. 用户角色与场景

- **借用方（全员）**：想用别人的闲置算力跑自己的工具。场景：打开目录 → 按模型过滤 → 认领 → 拿配置接入。
- **分享方（owner）**：关心自己的名额有没有被囤积、被谁用了。
- **管理员**：关心目录健康（离线节点、囤积行为），已有吊销/暂停/清除工具。

核心诉求：借用方「快、准、少折腾」；分享方「不被占坑」；管理员「可治理」。

## 4. 需求范围

### 本期范围（0.9.0 目录体验 + 1.0 治理随远程部署）
- M1 目录排序与可用性分层（前端）
- M2 模型过滤 chips + 「只看可认领」开关（前端）
- M3 节点卡车道折叠（前端）
- M4 借用方有效认领上限（后端 + 卡面映射）
- M5 空态/异常态文案补全

### 不包含
- 搜索框（模型 chips + 10-100 节点规模下无必要）
- 节点收藏 / 常用节点
- 到期自动重认领（renew 已有手动按钮）

### 依赖与前置
- M4 后端部分随远程后端部署生效（与 renew/rebind/admin 健康列同一批）。
- 不依赖任何新表/新迁移（validClaims 计数用现有内存态）。

## 5. 核心模块与规则

### 5.1 M1 目录排序与分层

**分层定义（互斥，从上到下）：**
- **T1 可认领**：`state === "active" && open && slotsLeft > 0 && availableTokens > 0`（任一车道满足即节点入 T1）
- **T2 等待开放**：不满足 T1，但 `open === false`（时段窗未开）且 `slotsLeft > 0 && availableTokens > 0`
- **T3 已耗尽/已暂停**：其余（含 exhausted、slotsLeft === 0、suspended）

**排序规则（同层内）：**
1. 剩余预算比例 `availableTokens / budgetTokens` 降序
2. 心跳新鲜度升序（并列时）
3. 节点标题字典序（最终稳定）

**交互**：T1/T2 正常渲染；T3 折叠进列表尾部的弱化分组「暂不可认领（N）」，可展开查看（保留存在感，不隐瞒）。

### 5.2 M2 模型过滤 chips + 只看可认领

- chips 数据源：目录中全部车道的 models 字段去重生成（通配符按前缀展示，如 `gemini-*`）；节点数为 0 的族不出现。
- 默认选中「全部」；选中某族后只显示 models 匹配该族的车道（模式匹配规则与认领门控一致：精确或通配）。
- 「只看可认领」开关默认开：隐藏 T2/T3 节点卡（目录头部计数仍显示其数量）。
- 两个控件位于目录标题右侧同一行，均为会话内状态（不持久化——目录是低频操作面）。

### 5.3 M3 节点卡车道折叠

- 节点卡默认展示全部车道，但车道数 > 3 时只展示前 3 条 + 「展开其余 N 条」；展开状态在该节点卡上保持到刷新。
- T3 分组内的节点卡默认折叠为单行摘要（标题 + 原因 + 展开箭头）。

### 5.4 M4 借用方有效认领上限

- 规则：同一 participantId 的 `state === "valid"` 认领数 ≥ `MAX_ACTIVE_CLAIMS_PER_BORROWER`（常量 5，代码内可调）时，`POST /api/shares/claim` 返回 `409 too_many_active_claims`，body 携带 `{ active: N, max: 5 }`。
- 卡面映射：「你有 N 把有效 Key（上限 5），先撤销再认领」；错误码进 apiPost 映射表。
- 不做白名单/管理员豁免（管理员可通过吊销间接释放；出现真实需求再加）。

### 5.5 M5 状态与文案

- 目录空态（无任何在线节点）：「暂无在线分享节点。」（现状保留）
- 过滤后空态：「没有匹配「{族}」的可认领车道。」+ 「清除过滤」按钮。
- 全被隐藏（只看可认领开）：「N 个节点暂不可认领」弱化行常驻。

## 6. 页面结构（文字原型，算力借用 Tab）

```
┌ 可认领节点                                    [全部] [gemini-*] [gpt-*]  ☑只看可认领 ┐
│ ▸ Sky-Macbook CPA                        在线 · v0.3.1 · 2/5 名额                  │
│   ├ Gemini 周额度  gemini-*  每周·22:00-14:00  222/2.0亿      [认领]              │
│   └ codex 闲置    gpt-*     每天·全天         0/5000万       [认领]              │
│ ▸ 张三的 CPA                             在线 · 0/3 名额（时段未开）               │
│ …                                                                                   │
│ ── 暂不可认领（4）─────────────────────────── [展开] ──                              │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

排序示例：同 T1 内「剩余比例高」在前；份额 2.0亿 剩 99.99% 排在 5000万 剩 100% 之后（比例优先于绝对值，鼓励把大盘算力用起来）。

## 7. 验收标准（可测试）

1. 构造 3 节点（A：T1、B：T2 时段未开、C：T3 满员）→ 目录顺序 A、B、C，C 在折叠分组且计数正确。
2. 选中 `gpt-*` chip → 仅显示服务 gpt 车道的节点；「只看可认领」关闭后 B/C 重新出现。
3. 借用方已有 5 把 valid Key 时认领第 6 把 → 409 too_many_active_claims，卡片显示中文提示与当前数量。
4. 吊销一把后再次认领 → 成功（上限按 valid 实时计算）。
5. 车道 5 条的节点卡默认显示 3 条 + 展开按钮；刷新后回到折叠态（会话内状态即可）。
6. 目录为空 / 全部被过滤：空态文案正确，「清除过滤」恢复全量。
7. 现有 e2e（认领/暂停/吊销/测试连接/续期）全部保持通过。

## 8. 影响范围

- **前端（插件卡 0.9.0）**：renderBorrow 重构（排序/过滤/折叠为纯函数 + 渲染两层）、apiPost 错误映射 +1。
- **后端**：handleClaim 增加借用方有效认领计数检查（一处）；常量 MAX_ACTIVE_CLAIMS_PER_BORROWER。
- **不受影响**：owner 控制台、认领/心跳/结算协议、CPA 插件、i18n 既有键。
- **部署门控**：M4 需要远程后端部署（与 renew/rebind 同批）；M1-M3 纯前端随卡版本即生效。

## 9. 风险与边界

- 上限数值 5 是拍板值：太小影响正常多节点使用，太大失去治理意义——上线后观察 admin 在用认领分布再调。
- 排序用「剩余比例」而非绝对量：小节点永远排前面可能不符合「要大池子」的直觉——提供了 chips 与排序即可切换心智；如反馈差再引入「按剩余量排序」选项。
- 节点很多时 /api/shares 全量返回的体积（每节点约 1KB）：100 节点约 100KB，可接受；超 500 节点再考虑服务端分页。

## 10. 度量与后续（不新增埋点，用 admin 现有数据观察）

- 目录规模趋势（在线节点数 / 车道数）：admin 概要行已有。
- 认领分布：admin 在用认领列——用于校准上限 5 与发现囤积。
- 后续候选（本期不做）：健康度评分（心跳稳定率）、owner 信誉、借出成交率排序。

## 11. 开放决策点

1. 上限 5 是否认可？（§5.4）
2. T2「等待开放」节点默认展示（含下次开放时间）还是并入折叠分组？（现方案：展示，因为「马上要开的节点」对借用方有价值）
3. 模型 chips 是否需要持久化上次选择？（现方案：否）
