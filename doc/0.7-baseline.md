## 1. Problem Definition

The current desktop client exposes real capabilities, but the information architecture still forces users to move between `Today`, `Trend`, and nested `Settings` panels to answer one primary question: how much did I use, what caused it, and whether the app is ready to keep tracking.

The UX demo in `doc/0.7.0-desktop-demo.html` gives the right direction: a single token workstation with overview, workdir analysis, source management, and settings surfaces. The design should be adapted to the real product model, not copied as static demo data.

## 2. Success Criteria

- Desktop first screen shows a useful local token workstation without requiring cloud configuration.
- Primary navigation becomes `Overview`, `Workdirs`, `Sources`, `Settings`.
- `Overview` combines today's total, token composition, trend context, top models, top workdirs, source readiness, and cloud/sync status.
- `Overview` range controls update the visible aggregate consistently across total, cost, composition, trend, top models, and top workdirs.
- `Workdirs` becomes a first-class analysis surface for public workdir names, aliases, contribution, trend, and model split.
- `Sources` remains the source of truth for provider enablement, detected/manual/preset sources, ignore/restore/delete, Cursor tokens, and scan cadence.
- `Settings` keeps profile, display behavior, language, cloud, update policy, diagnostics, reset, import, and export controls discoverable.
- Global rail/window controls show local/cloud readiness, scan row count, last scan, and update readiness without forcing the user into Settings.
- Desktop tray/menu bar controls let users reopen the Overview surface, inspect a compact today summary, and quit the app without depending on the Dock/taskbar window entry.
- macOS users can hide or restore the Dock icon from Settings without losing the tray/menu bar entry point.
- Shared drawers and feedback states provide drill-down details without reintroducing dense default tables.
- All user-facing strings use `src/shared/i18n.js` for `zh-CN` and `en`.
- The redesign does not upload prompts, assistant responses, source code, real absolute paths, Cursor session tokens, or identity private keys.

## 3. Key Constraints

- The UI must not show fake hourly analytics. Hourly usage rows are now valid for sync/storage when providers emit `hour`, but desktop charts still need explicit product wiring before presenting an hourly trend.
- `totalTokens` remains `inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens`; reasoning tokens remain diagnostic only.
- Estimated cost is optional display, never ranking truth.
- Cloud is optional. Local scan, overview, workdir analysis, and source management must work without `apiBaseUrl`.
- Source model stays as implemented in 0.6: provider enablement, manual sources, auto-detected sources, ignored auto sources, and preset sources are separate concepts.
- Cursor account/token material must stay local. The UI may show account labels only when they come from current local health/config state and are safe for the current surface.
- Tray/menu bar summary data must come from the same local usage cache and scan path as Overview. It must not introduce a second token aggregation rule.
- Dock visibility is a macOS-only runtime behavior. Windows must keep taskbar semantics while still supporting tray icon, tray menu, and explicit quit.
- Desktop UI changes use dev-mode verification by default. Packaged verification is required only when the change can differ after bundling or installation, such as package resources, bundled assets, presets, updater/release metadata, or install/download UX.
- Collector correctness is release-critical. Local Codex/Claude totals must be checked against unified `ccusage claude` / `ccusage codex` output with `npm run verify:ccusage` before release tagging or package-runtime handoff.

## 4. Scope

### 4.1 Desktop Information Architecture Redesign

**Goal**: Replace the current `Today / Trend / Settings` desktop navigation with `Overview / Workdirs / Sources / Settings`.

**Design**:

- `Overview`: default surface after onboarding and normal launch.
- `Workdirs`: first-class analysis and alias management surface.
- `Sources`: first-class source management surface, no longer buried in Settings.
- `Settings`: app, profile, cloud, update, diagnostics, reset, import/export, and advanced preferences.

**Rejected alternatives**:

- Keep `Today` and `Trend` as separate primary entries: it preserves the current fragmentation and does not match the user's first task.
- Copy the marketing demo HTML into the desktop shell directly: it bypasses i18n, real IPC/data state, privacy rules, and existing settings effect semantics.

### 4.2 Overview Workstation

**Goal**: Make the first screen answer "what happened today, what changed, and is tracking healthy?"

**Design**:

- Large current total from today's local rows.
- Token composition cards for input, output, cache read, cache write, and reasoning diagnostic.
- Optional estimated cost summary when `showEstimatedCost` is enabled.
- Trend context using real daily/weekly/monthly aggregates from the existing local cache.
- Top providers/source summary from provider health.
- Top models and top workdirs with compact bars and drill-down entry.
- Cloud/sync/update readiness summary without making cloud a prerequisite.
- Range controls for today, 7 days, 30 days, and all cached rows. Changing range updates total, cost, composition, top providers, top models, top workdirs, and trend context together.
- A lightweight explanation/drill-down entry that states the token total rule and clarifies why reasoning tokens are diagnostic.
- A global local scan action that starts the same real scan path as the existing refresh flow.

**Boundary**:

- No fake hourly chart. If the range control includes `Today`, label it as today's daily aggregate or implement real hourly rows first.
- No new backend API required for local overview.
- No hardcoded trend bar randomization or demo totals in product code.

### 4.3 Workdirs Analysis Surface

**Goal**: Promote workdir analysis from a Today subsection and alias list into a complete workflow.

**Design**:

- Range controls based on real cached daily rows: today, 7 days, 30 days, all cached rows.
- Contribution list/map with public workdir display names only.
- Alias editing inline or in a detail drawer.
- Workdir detail drawer showing total tokens, composition, model split, and recent trend for that workdir.
- Empty state distinguishes "no local usage yet" from "source disabled" and "scan still running".
- Workdir cards show range-specific total and contribution information from real cached rows.
- Detail drawer supports alias save, usage history by supported ranges, and model structure.

**Privacy boundary**:

- Do not expose raw absolute paths by default.
- Alias edits save to existing `workdirAliases` config.

### 4.4 Sources Management Redesign

**Goal**: Keep 0.6 source semantics but make source status and actions easier to scan.

**Design**:

- Provider tabs or grouped cards for Codex, Claude Code, and Cursor.
- Each provider shows enablement switch, detection status, manual entries, auto-detected entries, ignored entries, and preset entries.
- Manual roots/tokens support delete.
- Auto-detected sources support ignore/restore.
- Add Codex location, Add Claude Code location, Add Cursor token remain explicit actions.
- Scan cadence controls remain near source management.
- Source action feedback differentiates saved config changes, scan refresh, ignored source, restored source, deleted manual source, and failed action.

**Boundary**:

- Toggle switch is a state control; delete/ignore/add/refresh are actions.
- Source actions save immediately according to the 0.6 settings effect model.

### 4.5 Settings Consolidation

**Goal**: Settings should be smaller and operationally clear after Sources moves to primary navigation.

**Design**:

- Profile: nickname, identity/config import and export.
- App: display preferences, raw/compact tokens, estimated cost visibility, language, launch at login.
- Cloud: API base URL, cloud reachability, compatibility, sync status, Sync now.
- About/Updates: client version, latest version, update policy, check update, download/restart, installer fallback.
- Data Protection: automatic daily-first-start backup enabled by default, manual backup, restore from backup, backup folder selection, open backup folder, clear backups, and retention days. The simplified UI does not render a backup file list.
- Diagnostics/Reset: diagnostics export, local reset, local + cloud reset where configured.
- Import/export remain available after Sources moves out of Settings.
- Client observability: renderer errors and important user actions, sidecar command start/end/error summaries, scan/sync/update-adjacent operations, usage cache, upload queue summary, sync manifest, and recent runtime log are available through the local diagnostics export.
- Diagnostics status: Settings lets the user set runtime log retention days, open the log directory, and clear only the runtime log without resetting config, cache, queue, backup, or cloud state.

**Boundary**:

- Preserve `instant_autosave`, `action_autosave`, `save_required`, and `next_cycle` semantics from 0.6.
- `Sync now` and `Check update` must not silently use unsaved `apiBaseUrl`.
- Check update, download/restart, installer fallback, Data Protection, diagnostics export, reset local only, reset local + cloud, import config, and export config must all be wired after the DOM restructure.
- Runtime logs stay local under `~/.ai-token-league/log/runtime.YYYY-MM-DD.log`, are plain text `.log` files pruned by retention days, and must redact tokens, private keys, signatures, real paths, raw prompts, responses, transcripts, and source files.
- Default runtime log retention is 3 days. The desktop no longer exposes size, event count, latest time, 500-event, or 2MB retention controls.

**Data Protection boundary**:

- Backup/restore covers only AI Token League client files under `~/.ai-token-league`: config, usage cache, upload queue, sync manifest, and runtime log.
- Default backup folder is `~/.ai-token-league/backup/`; automatic backup is enabled by default and can run without a prior folder selection.
- Automatic backup runs at most once per UTC day on app start or after backup settings are enabled, then applies day-based retention. Default retention is 7 days.
- Backups are sensitive local recovery files and may contain identity private keys and local Cursor tokens. They are not diagnostics bundles and should not be shared.
- Restore first validates version, scope, and entry hashes, then snapshots current client files into `.restore-backup-<timestamp>` before replacing them.
- Backup/restore does not include backend `data/db.json` and does not include Codex, Claude Code, or Cursor raw logs, prompts, responses, source files, or full transcripts.

### 4.9 Runtime Status and Supporting Contract Fixes

**Goal**: Make the redesigned desktop and public page consume accurate runtime state.

**Implemented design**:

- Desktop cloud status now invalidates stale release/update/sync-derived state when the saved API base URL changes.
- Rail/cloud status distinguishes local-only, checking, online, offline, and unavailable states from current config and API connection state.
- `Sync now` and `Check update` still guard against unsaved API base URL changes.
- Clicking `Overview` triggers a local usage refresh through the existing scan path so returning to the default analysis surface refreshes cached rows before rendering.
- Board summary now exposes identity display metadata (`identityMode`, `identityLabel`) so public copy can reflect the active board identity mode.
- OpenRouter warm refresh recalculates costs when fresh price cache exists but missing-price models remain.
- Card inline actions and destructive rows were restyled to keep row-level operations in context and make destructive actions visually distinct.
- Collector sidecar scans stream/cache large source sets instead of holding avoidable intermediate state, so desktop tray refresh and CLI scans stay usable on large local logs.
- Codex local parsing aligns completed local days with unified `ccusage codex`, including copied rollout and subagent replay deduplication; the verifier is an explicit release gate, not an optional manual comparison.
- Update checking runs periodically when Cloud Connection is configured, auto-downloads an available updater package, and requires an explicit user restart/install step.
- Updater installation is split into download and install/restart so a downloaded package can be retained as pending state instead of installing immediately from the check flow.

**Boundary**:

- This runtime-status supplement did not change the board upload contract, usage upload route, MySQL schema, participant identity private key storage, or token total rule. The later cloud usage snapshot sync supplement below is the explicit exception for usage sync contract and sync metadata storage.

### 4.10 Tray/Menu Bar Runtime Controls

**Goal**: Let the desktop client behave like a persistent local collector: users can reopen the app, inspect today's compact usage, and quit explicitly from the OS tray/menu bar. On macOS, users can optionally hide the Dock icon while keeping the menu bar entry point.

**Reason admitted mid-version**: 0.7 makes the desktop client the primary product surface. A local-first collector that runs background scans needs an OS-level entry point after the main window is closed or the Dock icon is hidden.

**Design**:

- Create one Tauri tray/menu-bar entry during app startup on macOS and Windows.
- Left click opens or focuses the desktop client on `Overview`.
- Right click opens a dynamic native menu with:
  - compact today's total token count,
  - input/output/cache summary when cached rows are available,
  - local row count and last scan time,
  - cloud/sync state when available,
  - `Open AI Token League`,
  - `Refresh now`,
  - `Quit`.
- `Refresh now` uses the existing local scan/sync path and updates the same usage cache consumed by Overview and Workdirs.
- `Quit` is the explicit exit path for tray mode. Closing the main window should hide or close the window without killing the background tray process unless the user chose `Quit`.
- Add a Settings > App behavior switch for macOS Dock visibility. When enabled, call `app.dock.hide()`; when disabled, call `app.dock.show()`.
- Persist the Dock preference in config, for example `hideDockIcon`, and apply it during startup and after saving Settings.
- Hide or disable the Dock setting on non-macOS platforms; Windows keeps the taskbar/window model and uses tray controls for reopen/summary/quit.

**Boundary**:

- Do not build a custom floating tray window for the first version; native tray menus are enough for the current requirement and reduce cross-platform risk.
- Do not open the public web download/home page on tray left click unless a later requirement explicitly changes "homepage" to mean external Web. The product home for the desktop client is `Overview`.
- Do not show raw absolute paths, Cursor session tokens, prompts, responses, source code, or private identity fields in tray/menu summaries.
- Do not add a new backend route or storage table for tray summaries.
- The tray total must follow the existing rule: `totalTokens = inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens`.

### 4.11 Cloud Usage Bucket Snapshot Sync

**Goal**: Make cloud usage converge to the local collector truth while preventing routine sync payloads from growing with all historical rows.

**Reason admitted mid-version**: Live cloud data showed stale rows can remain when a workdir hash disappears from local scans. The existing `/api/usage/daily-batch` path is upsert-only: every client upload sends all scanned rows, but the server has no signed scope that says which old rows are now absent. A sync protocol that cannot delete missing rows cannot guarantee board totals match the local usage cache.

**Protocol design**:

- Keep `POST /api/usage/daily-batch` as the endpoint.
- Snapshot-capable clients use protocol version 2. `src/shared/version.js` should expose a named `SNAPSHOT_PROTOCOL_VERSION = 2`; rollout policy can then require `clientProtocolVersion >= SNAPSHOT_PROTOCOL_VERSION`.
- Add signed `snapshot` metadata for new clients:
  - `mode`: `device_day_hour_provider` for current hourly-capable clients; `device_day_provider` remains accepted for legacy/day bucket tests and compatibility
  - `day`: the bucket day, formatted `YYYY-MM-DD`
  - `hour`: integer `0..23` when `mode` is `device_day_hour_provider`
  - `providerId`: one provider only, for example `codex_local` or `claude_code_local`
  - `bucketFingerprint`: stable hash of the sorted bucket rows
  - `rowCount` and `totalTokens`: diagnostic totals for server validation and operations
- New client signing payload must include `participantId`, `deviceId`, `clientGeneratedAt`, optional `client`, `snapshot`, and `items`.
- Every item in a snapshot request must belong to the same `participantId + deviceId + day + hour + providerId` bucket for hourly mode, or the same `participantId + deviceId + day + providerId` bucket for day mode. Mixed-day, mixed-hour, mixed-provider, or mixed-device snapshot uploads are rejected.
- `bucketFingerprint` is an upload dirty-check and idempotency key, not the correctness authority. Re-uploading the same bucket must be safe even when the fingerprint changes after local token aggregation changes.
- Fingerprint input is exactly the sorted list of these per-row fields: `day`, `hour`, `toolCode`, `providerId`, `workdirHash`, `workdirDisplayName`, `model`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `reasoningTokens`, `totalTokens`, `sourceQuality`, `sourceFingerprint`. Exclude `rawSourceRef`, `providerVersion`, `parserVersion`, all cost fields, upload timestamps, aliases, and diagnostics.
- Server behavior for snapshot requests:
  1. verify signature over the snapshot-aware payload,
  2. upsert incoming rows by `hourlyUsageKey` for hourly mode or `usageKey` for day mode,
  3. delete rows in the same signed bucket scope whose row key is not in the incoming item set,
  4. record bucket sync metadata for idempotency and diagnostics.
- Snapshot idempotency is owned by bucket metadata and fingerprint comparison, not by the existing `upload_batches` payload hash. A repeated snapshot with a new `clientGeneratedAt` can bypass batch-level duplicate detection and still must converge to the same bucket state.
- MySQL bucket replace must use an incremental write path, not the current `syncAllTables()` full flush. It must run in one transaction: register/update identity rows as needed, upsert incoming usage rows, delete stale rows with a bucket-scoped `DELETE ... WHERE participantId=? AND deviceId=? AND day=? AND hour=? AND providerId=? ...` for hourly buckets or day/provider equivalent for legacy day buckets, then write bucket metadata before commit.
- The bucket transaction scope remains `participantId + deviceId + day + hour + providerId` for hourly mode, so a future request-local implementation can allow different buckets to proceed independently.
- Production MySQL deployments may run multiple backend instances against the same database. Until the MySQL write path is fully request-local and no longer reuses the store-level usage mirror, every MySQL write entrypoint also takes a database-level named lock. This intentionally serializes MySQL writes across instances and is controlled by `MYSQL_WRITE_LOCK_NAME` / `MYSQL_WRITE_LOCK_TIMEOUT_SECONDS`.
- Server behavior for requests without `snapshot` remains the historical upsert-only behavior.

**Client design**:

- Local scan remains the source of truth and now preserves `hour` where available. Daily aggregate rows are derived from hourly rows for board/detail compatibility.
- Before syncing, the client groups rows into `day + hour + providerId` buckets for hourly-capable data.
- The client stores a local sync manifest with per-bucket fingerprint, row count, total tokens, and last successful sync time in an independent file, defaulting to `~/.ai-token-league/sync-manifest.json`. Do not put the full manifest into `config.json`.
- Manifest writes must be atomic (`write temp file` then `rename`). If the manifest is missing, unreadable, or corrupt, treat it as no manifest and perform full bucket snapshot sync.
- If no protocol-v2 manifest exists, the client must perform one full bucket snapshot sync: upload every local bucket with replace semantics. This first sync is intentionally not optimized for bandwidth; its purpose is to converge cloud state to local truth.
- First full bucket sync should use bounded concurrency, defaulting to a small value such as 3 to 5 requests, so CLI and desktop sync do not block behind hundreds of serial buckets.
- After first full bucket sync, routine sync uploads only buckets whose fingerprint changed.
- Desktop auto-sync should use "has dirty bucket fingerprint" as the trigger. Existing global `syncStatus.sourceFingerprint` becomes legacy diagnostic state and must not be the protocol-v2 auto-sync authority.
- Offline queue entries are bucket snapshots, not all-history snapshots. Replaying a queue item must be idempotent for the same signed bucket fingerprint.
- Existing offline queue files can contain legacy whole-history signed payloads. Queue drain must accept both legacy queue entries and protocol-v2 bucket snapshot entries during upgrade. Use `entry.payload.snapshot` presence as the format discriminator. Legacy queued entries are uploaded with upsert-only semantics and must not be converted into deletion-capable snapshots.
- A manual or CLI full resync should clear or ignore the local manifest and re-upload all local buckets as snapshot requests.

**Compatibility**:

- Historical clients do not send `snapshot`; the server must continue accepting them as upsert-only uploads.
- Historical clients must not trigger deletion, because they do not sign a deletion scope.
- New clients may coexist with historical clients during rollout. Snapshot uploads converge buckets touched by new clients; old clients can still append/upsert until a minimum-client policy is enabled.
- During the coexistence window, a historical client can re-upsert a row that a snapshot-capable client just deleted. This is an accepted rollout tradeoff, not a correctness guarantee. Production convergence requires either all active clients to upgrade or a later `MIN_CLIENT_ENFORCE=true` gate.
- After a compatibility window, `MIN_CLIENT_ENFORCE=true` may be used to block clients below the snapshot-capable version if stale-row risk remains unacceptable.

**Storage**:

- Add sync metadata stores for bucket idempotency and diagnostics. In MySQL these are `usage_sync_buckets` for day buckets and `usage_sync_buckets_hourly` for hourly buckets; in JSON storage, add equivalent objects under the database root.
- The bucket metadata is not ranking truth. `usage_daily` remains the source for leaderboard/detail/trend/admin views, while `usage_hourly` is the storage source for hourly snapshot replacement and daily derivation.
- Suggested hourly bucket key: `participantId|deviceId|day|hour|providerId`.
- Required hourly bucket fields: `participantId`, `deviceId`, `day`, `hour`, `providerId`, `granularity`, `bucketFingerprint`, `rowCount`, `totalTokens`, `clientGeneratedAt`, `syncedAt`, `updatedAt`.
- The existing `upload_batches` table remains a legacy batch audit and duplicate-detection aid; it is not the protocol-v2 idempotency authority.

**Boundaries**:

- Do not add prompt, assistant response, source code, real absolute path, Cursor session token, or identity private key fields to snapshot payloads.
- Do not delete across providers when syncing one provider bucket.
- Do not delete across hours when syncing one hourly bucket.
- Do not delete across devices; device-scoped uploads only replace the uploading device's bucket.
- The first snapshot protocol assumes one `providerId` maps to one `toolCode`. If a future provider can emit multiple tool codes under the same provider id, either include `toolCode` in the snapshot scope or split that provider before enabling delete.
- Do not initialize a missing client manifest as "already synced". Missing manifest means cloud state is unknown and requires a full bucket snapshot sync.
- Do not make bandwidth reduction the first-sync goal. First sync correctness is higher priority than payload size.
- Do not add empty-bucket deletion in the first version. If a local day/provider bucket no longer exists at all, deleting the cloud bucket needs an explicit later design because it can erase data after local log loss or provider disablement. Provider disablement therefore leaves historical cloud rows intact; UI may show that the provider is disabled or stale, but sync must not infer deletion from absence.

### 4.12 Public Leaderboard Scheme A

**Goal**: Redesign the public leaderboard around a compact first viewport: a single-line masthead, shared Top 3 medal cards, and a view switch that changes only the #4-and-below content between Meter and List.

**Reason admitted mid-version**: 0.7 is primarily a desktop UI/UX redesign, but the public leaderboard is a release-visible companion surface. The existing table-like layout spends too much first-screen space on masthead and does not differentiate the top participants. Scheme A keeps the ranking truth unchanged while improving scan density and making the Top 3 visually legible.

**Design**:

- Masthead is a single compact header: `AI Token League` at 28px, one identity pill for the active board mode, home navigation, and language switcher.
- Anonymous/public/authenticated identity is communicated once in the header pill. Rows and cards do not repeat per-name anonymous badges.
- Top 3 always render as medal cards above the switchable view in podium order: rank 2, rank 1, rank 3. Gold, silver, and bronze are indicated by left border color and label; rank 1 is visually elevated. Each card shows rank, display name, compact total tokens, contribution, optional cost, and model-usage segments.
- Meter view is the default view for #4 and below: each row is 28px high, uses an 8px horizontal bar, right-aligns token values and contribution, and renders internal model-usage segments inside the normalized total bar. Hover text lists model token usage. The bar remains normalized against the largest #4-and-below total; contribution text uses the complete current-period leaderboard total.
- List view renders #4 and below as a table with columns `rank | name | total tokens | contribution | optional cost | models`. Contribution is the participant's `totalTokens` divided by the complete current-period leaderboard total. Model pills are visible only in List view and participant detail.
- The segmented view toggle stays auto-width in the toolbar; the choice persists to `localStorage`.
- Both views are populated on every data load so switching is instant without re-fetching.
- Estimated cost toggle, period filter, board identity mode, and detail drawer work identically in both views.
- All new user-facing strings use `src/shared/i18n.js` for `zh-CN` and `en`.

**Boundary**:

- Do not change the leaderboard API contract, ranking logic, or data source.
- Contribution is explanatory display only. It must use the complete current-period response as its denominator and must not replace `totalTokens` as ranking truth.
- Do not add backend routes or storage for view mode preference.
- View switching never hides the Top 3; it only changes the #4-and-below presentation.
- Meter view does not show model pills inline; model usage is encoded as bar segments and hover text. Full model pills remain visible in List view and the detail drawer.
- The Meter component reuses the desktop color variables (`--teal`, `--yellow`, `--violet`) added to the web stylesheet; it does not import desktop CSS.

### 4.13 Self-Hosted Tauri Release Orchestration

**Goal**: Make self-hosted Tauri release publishing deterministic for split platform build hosts and prevent incomplete updater/install metadata from being published as complete.

**Reason admitted mid-version**: The release pipeline moved from legacy Electron-style `releases/` metadata to Tauri updater/install metadata. A single macOS host cannot be treated as the official full-platform builder, and split macOS/Windows/Linux hosts need a merge point that verifies required platforms and checksums before clients see the update.

**Design**:

- Self-hosted Tauri metadata defaults to `tauri-releases/`, not the old Electron `releases/` path.
- Publishing mode is explicit:
  - `--part`: upload only the current platform artifacts and `parts/<platform>.json`.
  - `--finalize`: read all required platform parts, validate them, then publish global `tauri-update.json`, `installer.json`, `latest.json`, and `checksums.txt`.
  - `--full`: publish a complete local `dist/` in one trusted environment.
- `scripts/release.sh --upload` for a single platform writes platform part metadata; final merged metadata is produced only by `node scripts/publish-release.js --finalize`.
- `RELEASE_REQUIRED_PLATFORMS` is the completeness contract. Local/private deployments may intentionally omit Linux by setting the required list, but missing required platforms must fail finalize.
- `checksums.txt` must include every deduplicated updater and installer artifact that appears in finalized metadata. Complete `tauri-update.json` and `installer.json` are not sufficient evidence on their own.
- Public server runtime reads static metadata and platform installer lists only; it never needs OSS write credentials.

**Boundary**:

- Do not use `--platform all` on macOS as the official Windows/Linux release path. It is a diagnostic path unless a real matching build host produced the artifacts.
- Do not let publish defaults silently choose full, part, or finalize mode. Mode ambiguity is a release-risk bug.
- Do not publish release metadata into the legacy `releases/` path for Tauri clients unless a separate compatibility design requires it.

### 4.14 Community Analytics Participant Ranking

**Goal**: Make the existing analytics page answer the community-level question "who contributed the most tokens in this period?" without forcing users into the separate leaderboard page.

**Reason admitted mid-version**: Both the public analytics page and the admin embedded analytics page already expose a community/person selector, but the community scope had no visual participant comparison. This is a narrow, release-visible web improvement that reuses the existing analytics aggregation and ranking truth.

**Design**:

- The analytics API returns `participantRanking` only for community scope, aggregated by the selected period using the existing `totalTokens` ranking rule.
- The analytics page renders a participant treemap below the provider breakdown when `全社区` / `All Community` is selected; rectangle area represents each displayed participant's period total, and the card is hidden for individual analysis.
- The public board response transforms ranking entries through the existing public/anonymous identity mapping before returning them. Admin analytics keeps participant nicknames for the authenticated admin surface.
- The card displays at least twelve participants, or half of the community when that is larger, as separate rectangles and aggregates the remainder into `其他人员`; the chart height grows with the displayed count, and any label that cannot fit inside a small rectangle is shown in a readable label rail below it.
- All new labels are localized through `src/shared/i18n.js` for `zh-CN` and `en`.

**Boundary**:

- Do not change ranking truth, cost semantics, participant identity storage, or the existing leaderboard route.
- Do not expose real participant IDs in anonymous public analytics responses.
- Do not show the community ranking card while an individual participant is selected.

### 4.15 Editorial League × Control Room Web Refresh

**Goal**: Give the public Web a composed editorial league identity and give Admin a denser control-room identity, while keeping the existing API, data meaning, authentication boundary, and interaction contracts intact.

**Reason admitted mid-version**: The public download, leaderboard, analytics, and Admin pages already had the necessary real data and interactions, but their visual hierarchy had drifted into separate CSS treatments. A single scoped Web refresh is the shortest path to improve perceived quality without rewriting the backend or duplicating chart logic.

**Implemented design**:

- Public pages use a low-contrast paper grid on the page background only, Fraunces for brand/display numbers, IBM Plex Sans for interface text, and IBM Plex Mono for data values.
- The home page presents Today/Yesterday, This week/Last week, and This month/Last month as three paired scoreboards; the 30-day trend is the first chart stage, Today Top links directly to the full leaderboard, and supporting analysis/download surfaces follow below.
- The leaderboard restores an explicit title, gives the Top 1 brass visual priority, keeps Top 2/3 as supporting podium cards, and keeps #4+ in the existing Meter/List views.
- Analytics gives token composition a real secondary column, keeps the participant treemap and existing chart renderers, and preserves period, participant, cost, tooltip, and detail interactions.
- Admin keeps the existing tabs and API calls but separates operational controls, view state, tables, pricing priority, quality/device status, and destructive actions visually. Long workdir/model/IP values remain bounded and retain tooltip access.
- Admin analytics keeps the existing iframe and `analytics-resize` `postMessage` protocol. Inline fixed height is removed from HTML; the iframe uses an Admin container and the embedded page hides public masthead context via `is-embedded` CSS.
- A shared motion language covers page entry, initial data loading, period/view changes, chart drawing, leaderboard row landing, and Admin tab/panel refresh. Motion communicates pending and completed work, remains lightweight, and collapses to near-zero duration under `prefers-reduced-motion`.
- Three self-review rounds close the implementation: structure/contract review, real-browser responsive and interaction review, then maintainability/delivery review. The browser round covers 1440px, 1280px, and 390px until no P0/P1 usability or hierarchy issue remains.

**Verification evidence**:

- Four Web entry scripts pass `node --check`; the Node backend/shared/Web structure suite passes through `npm test`; `git diff --check` is clean.
- Headless Chromium at 1440px, 1280px, and 390px reports no page-level horizontal overflow on home, leaderboard, analytics, or Admin. At 390px the Admin usage table scrolls inside `.table-wrap` (`980px` content within a `364px` container).
- Admin tabs, pricing form grouping, embedded analytics auto-height, English navigation, leaderboard detail Escape close, and focus restoration were exercised against an isolated copy of the local JSON store.
- The in-app browser additionally exercised the visible loading capsule, chart/data landing state, Admin 25-row loaded table, navigation controls, and reduced-motion CSS boundary. An experimental cross-document transition was rejected during review so ordinary navigation remains the source of truth.

**Boundary**:

- This is a temporary/opportunistic UI refresh inside 0.7: it adds only HTML wrappers, CSS classes, i18n references, client-side loading state, and presentation behavior; it does not add or change backend routes, database fields, storage structures, authentication, ranking truth, or iframe message semantics.
- The existing `doc/demos/web-ui-refresh-static.html` remains a demo asset and is not a production source of truth.
- No new image asset, fake metric, heavy UI dependency, prompt, source code, real path, or identity secret is introduced.

## 7. Rules

- Do not split this redesign into partial product phases in the baseline. Task cards may be parallelized, but acceptance is one complete client redesign.
- Do not add hourly analytics unless the data model is implemented and verified.
- Do not confuse hourly sync/storage with a user-facing hourly analytics feature. UI exposure still needs explicit product wiring and verification.
- Do not trade away privacy boundaries for visual fidelity.
- Do not make the marketing demo the source of truth for runtime data, security, or configuration semantics.
- Do not make tray close behavior ambiguous. The user-facing app must have a clear explicit `Quit` action when closing the window no longer exits the process.
- Do not let legacy upload requests delete cloud rows. Deletion requires a signed snapshot scope.
- Do not optimize away the first protocol-v2 full bucket sync. Missing manifest means the client has not proven cloud convergence.
