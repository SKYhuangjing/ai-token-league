# AI Token League 0.3 开发任务

## 0. 范围

0.3 聚焦客户端与服务端兼容、客户端版本可见、自升级准备。

来自 `roadmap.md` 的计划功能：

- API 数据上报增加兼容版本信息校验。
- 客户端版本信息。
- 客户端自升级能力。

成功标准：

- 服务端可以在接收 usage 数据前识别不兼容客户端。
- Desktop 和 CLI 可以展示本地版本、服务端版本、最新版本和兼容状态。
- 用户可以发现并应用新的 macOS arm64、macOS Intel x64 或 Windows x64 客户端，且不会丢失本地身份或待上传 usage。

## 2. 产品需求

### R1 API 数据上报校验兼容版本信息

问题：

- 0.2 只校验身份签名，payload 结构主要依赖隐式约定。
- 当客户端上报契约演进后，旧客户端可能提交服务端无法安全解释的数据。

成功标准：

- 客户端在设备注册和 usage 上报时发送 app/protocol/platform/build 元数据。
- 服务端有统一的兼容策略，覆盖允许、提醒、拒绝三类结果。
- 被拒绝的 upload 不会清空本地上传队列。
- 响应能告诉客户端：已接受、建议升级、或必须升级。

### R2 客户端版本信息

问题：

- 用户和运营者无法直接判断当前运行的是哪个 Desktop/CLI 构建，也无法判断它是否匹配服务端。

成功标准：

- Desktop Settings / System 展示 app 版本、平台、API 目标、服务端版本、最新版本、兼容状态和上次检查时间。
- CLI health/status 展示同一组核心字段。
- macOS arm64、macOS Intel x64、Windows x64 打包产物携带正确 app 版本。

### R3 客户端自升级能力

问题：

- 0.2 分发依赖手工共享重新生成的包。
- 如果没有直接升级路径，就不能可靠地强制旧客户端退出兼容窗口。

成功标准：

- 服务端或发布宿主提供公开可读的 update manifest。
- 客户端可以检查是否有新版本。
- 客户端可以按当前平台下载 artifact，并校验 checksum。
- 升级保留 identity、config、tokens、aliases、usage cache 和 upload queue。
- 升级失败不会破坏当前安装。

### R4 OSS 发布资源托管

问题：

- 自升级需要一个客户端可公开读取、发布脚本可自动写入的 release 资源位置。
- 上传凭据属于发布侧权限，不能进入客户端、manifest、README 或示例配置真实值。

已确认方案：

- 使用阿里云 OSS，S3 协议兼容上传，但 endpoint/bucket/prefix 不写死在代码里。
- OSS release 配置融合现有本地 env 体系：`env.example` 提供占位键，`env.local` / `env.test` / CI Secret 提供真实值。
- 发布脚本和 app-server 读取同一组 release env，生成 manifest URL、artifact URL 和 OSS upload path。
- 资源公开读，由 OSS bucket/prefix 权限控制。
- AK/SK 只通过本地环境变量或 CI Secret 注入发布脚本，app-server 和客户端不持有 OSS 写权限。
- 开源阶段暂不做 manifest 签名；manifest authenticity 依赖 OSS 权限边界和发布流程，artifact 完整性通过 sha256 checksum 校验。
- 如后续进入更强分发安全需求，再恢复 manifest 非对称签名任务。

Release env keys：

```text
RELEASE_OSS_ENDPOINT=oss-cn-shanghai.aliyuncs.com
RELEASE_OSS_BUCKET=1data-dev
RELEASE_OSS_PREFIX=ai-token-league
RELEASE_PUBLIC_BASE_URL=https://1data-dev.oss-cn-shanghai.aliyuncs.com/ai-token-league
RELEASE_MANIFEST_PATH=releases/latest.json
RELEASE_OSS_ACCESS_KEY_ID=...
RELEASE_OSS_ACCESS_KEY_SECRET=...
```

权限边界：

- `RELEASE_OSS_ENDPOINT`、`RELEASE_OSS_BUCKET`、`RELEASE_OSS_PREFIX`、`RELEASE_PUBLIC_BASE_URL`、`RELEASE_MANIFEST_PATH` 可进入 app-server env。
- `RELEASE_OSS_ACCESS_KEY_ID`、`RELEASE_OSS_ACCESS_KEY_SECRET` 只允许进入发布脚本运行环境或 CI Secret。
- `env.example` 只能放占位值，不能放真实 AK/SK。

按上述 env 解析后的发布资源路径：

```text
oss://${RELEASE_OSS_BUCKET}/${RELEASE_OSS_PREFIX}/${RELEASE_MANIFEST_PATH}
oss://${RELEASE_OSS_BUCKET}/${RELEASE_OSS_PREFIX}/releases/<version>/AI Token League-darwin-arm64.zip
oss://${RELEASE_OSS_BUCKET}/${RELEASE_OSS_PREFIX}/releases/<version>/AI Token League-darwin-x64.zip
oss://${RELEASE_OSS_BUCKET}/${RELEASE_OSS_PREFIX}/releases/<version>/AI Token League-win32-x64.zip
oss://${RELEASE_OSS_BUCKET}/${RELEASE_OSS_PREFIX}/releases/<version>/checksums.txt
```

客户端公开读取入口：

```text
${RELEASE_PUBLIC_BASE_URL}/${RELEASE_MANIFEST_PATH}
```

安全边界：

- 客户端只读取公开 URL，不持有 OSS 写权限。
- 发布脚本先上传 versioned artifact，再生成 checksum，再生成 manifest，最后覆盖 `latest.json`。
- `latest.json` 覆盖必须作为最后一步，避免客户端读到尚未完整上传的版本。
- 当前 manifest 不签名。这个取舍的原因是项目计划开源，客户端内置 public key 的收益有限；真正的写入权限仍由 OSS AK/SK 和发布流程控制。

### R5 Cursor 首装本地 token 检测状态表达

问题：

- 首次安装时 Cursor provider 默认 Off，避免未确认前访问 Cursor Dashboard API。
- 本机 Cursor token 可以被 health 检测到，但 Settings 的 token summary 只统计手动保存 token，容易让用户误判为“没有自动检测到 Cursor token”。

成功标准：

- Sources / Cursor 继续由 On/Off 控制是否联网扫描 Cursor Dashboard usage。
- Settings token summary 同时表达手动 token 和本机自动检测账号。
- 未检测到账号时，文案使用 account detected 口径，不再把自动检测误写成 configured。
- 不把自动检测 token 写入 config，不展示真实 token，不改变隐私边界。

### R6 Web 客户端下载入口

问题：

- 0.3 已经具备三平台 release artifact 和 OSS manifest，但 Web 首页没有清晰的客户端下载入口。
- 下载入口如果直接放在榜单筛选前，会占用公共榜单的数据查看路径。
- Web 页面不能内置 OSS manifest URL，也不能绕过 app-server 形成第二个 release truth source。

成功标准：

- `http://127.0.0.1:8787/` 首页提供客户端下载入口。
- 下载入口默认不阻塞排行榜筛选和数据查看，展开后再展示三平台 artifact。
- Web 只请求 app-server release API；app-server 负责读取 release env、拉取并校验 manifest。
- Web 不展示 AK/SK、OSS bucket 写入信息或本地 env 细节。
- app-server 未配置 release 时，页面展示产品化不可用状态，而不是工程配置错误。

## 6. 实现结果

本批任务已按 `0.3.0` 落地：

- `src/shared/version.js` 定义 app/server/protocol/platform/build 元数据与统一兼容策略。
- `src/backend/server.js` 在 register、daily-batch、health 复用兼容策略；不兼容上报返回 `426`，客户端保留队列。
- `src/collector/cli.js` 的 `health` / `status` 输出 client、server、latest version 和 compatibility。
- Desktop Settings / System 展示 client/server/latest/compatibility/update check 状态，支持手动检查更新、下载 artifact、sha256 校验和显式升级交接。
- Desktop Settings / Sources 的 Cursor 区分手动保存 token 和本机自动检测账号；Cursor 仍默认 Off，只有用户打开后才扫描 Cursor Dashboard usage。
- Desktop 在开启后台刷新并配置 API 后，每 6 小时做一次后台 update check。
- `scripts/zip-dist.js` 为三平台 zip 生成 `dist/checksums.txt`。
- `scripts/publish-release.js` 从 env/env.local 读取 OSS release 配置，dry-run 或发布三平台 artifact、`checksums.txt`，并最后覆盖 `RELEASE_MANIFEST_PATH`。
- `src/shared/update.js` 定义 release config、manifest schema、platform artifact 选择和 checksum 校验 helper。
- `src/backend/server.js` 增加 `/api/release/latest`，由 app-server 拉取并校验 latest manifest 后返回公开下载信息。
- `src/web/index.html` / `src/web/app.js` 在 Public Web 首页提供折叠式 `Download client` 入口，展开后展示三平台 artifact，不占用榜单筛选和数据查看路径。

## 8. 0.3.0 设置产品接入复盘

### 8.1 问题定义

当前 Desktop Settings 的信息架构把“云端 API 目标”放在 Sync tab 下，但 System / Check update 也依赖这个 API 目标：

- `System -> Check update` 先读取本地 `apiBaseUrl`，请求 `/api/health`，再从 health response 里的 `release.manifestUrl` 获取 update manifest。
- 如果本地没有配置 `apiBaseUrl`，代码会尝试读取进程 env 中的 `RELEASE_PUBLIC_BASE_URL` 和 `RELEASE_MANIFEST_PATH`。
- 普通打包客户端通常不会带这些 release env，因此未配置 Sync API 时，System 的更新检查会显示 release manifest URL 未配置。

这不是 checksum、OSS 或 manifest schema 的问题，而是产品配置分组不清：更新能力属于产品云端能力，不应该被用户理解为“同步上传设置”的附属功能。

已确认收口：

- 不允许客户端内置 manifest URL。
- Check update 的唯一数据源是 app-server。
- app-server 负责读取 release env，并通过 `/api/health.release.manifestUrl` 或后续 release config API 暴露客户端可读的 manifest URL。
- 客户端只保存 Cloud Connection 的 API base URL，不保存 OSS endpoint、bucket、prefix、manifest URL，也不读取本机 release env。
- 这个取舍降低维护复杂度：release 地址、latest version、兼容策略都由 app-server 统一控制。

### 8.2 配置域重新划分

0.3.0 后续 UI 应按“本地设置 / 云端设置 / 系统设置”重新组合，而不是按当前 Profile、Display、Sync、Sources、Aliases、System 混排。

| 配置域 | 包含项 | 数据来源 | 说明 |
| --- | --- | --- | --- |
| 本地身份 | nickname、participantId、deviceId、identity import/export | `~/.ai-token-league/config.json` | 只影响本机身份和展示名，不依赖云端。 |
| 本地采集 | provider enabled、Codex/Claude roots、Cursor token、workdir aliases、usage cache | 本机配置和缓存 | 只控制本机扫描、别名和本地敏感凭据。 |
| 本地显示 | estimated cost、raw tokens | 本机配置 | 只影响 UI 呈现，不改变上传 payload。 |
| 云端连接 | API base URL、API health、server version、protocol compatibility、release manifest URL | 本机配置 + `/api/health` | 是服务端入口配置，供 sync、pricing、compatibility、update check 共用。 |
| 云端同步 | manual sync、background refresh、refresh interval、upload queue、last sync result | 本机配置 + upload queue + server response | 依赖云端连接，但不拥有 API base URL。 |
| 版本更新 | client version、latest version、check update、download artifact、checksum verify | 云端连接的 health/release manifest | 仅依赖 app-server，不允许客户端内置 manifest URL。 |
| 系统行为 | launch at login、reset local data | Electron / 本机文件 | 与云端无关，属于本机运行行为。 |

### 8.3 推荐的 Settings 导航

建议把 Settings 调整为 5 个 tab：

| Tab | 目标 | 当前内容迁移 |
| --- | --- | --- |
| Account | 本地身份管理 | Profile 的 nickname、export/import。 |
| Sources | 本地采集源和别名 | Sources + Aliases 合并，Cursor token 放这里。 |
| Cloud | 云端连接和兼容状态 | Sync 里的 API base URL、API health；System 里的 server version、compatibility、latest version 移到这里。 |
| Sync | 上传与后台刷新 | sync status、manual sync、background refresh、refresh interval、upload queue；只引用 Cloud 的 API target，不再拥有 API base URL。 |
| App | 客户端版本、更新、系统行为 | client version、check update、download verified package、launch at login、reset local data、display preferences。 |

核心原则：

- API base URL 是 Cloud Connection，不是 Sync 的私有配置。
- Update Check 是 App Version 能力，但它的数据源来自 Cloud Connection。
- Sync、Pricing、Compatibility、Update 都消费同一个 Cloud Connection 状态。
- 用户没有配置 Cloud Connection 时，App tab 仍应展示本地版本，并明确提示“配置 Cloud 后可检查更新”，而不是暴露 release env 缺失这种工程错误。
- 客户端不提供绕过 Cloud Connection 的 update manifest 配置入口。

### 8.5 0.3.0 代码变更落地结果

目标：让 Check update 只依赖 app-server，Settings 中显式建立 Cloud Connection，避免用户把 API base URL 理解为 Sync 私有配置。

已落地改动：

   - Sync 只展示当前 Cloud target、manual sync、background refresh、refresh interval、queue status。
   - App 展示 client version、latest version、check update、download verified package、launch at login、reset local data。
