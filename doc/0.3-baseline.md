# AI Token League 0.3 Baseline

Version: `0.3`
Drafted at: `2026-05-06`
Status: implemented baseline for client/server compatibility, client version visibility, and desktop update handoff.

This baseline starts from `0.2-baseline.md`. The 0.3 implementation is versioned as `0.3.0`.

## 1. Product Goal

0.3 turns AI Token League from a locally shared desktop bundle into an upgradable client/server product.

User-facing goals:

- Users can see which client version they are running.
- Users can know whether their client can still upload data to the current server.
- Users can discover and apply a newer desktop client without manually watching the repository.
- Server-side upload validation can evolve without silently accepting incompatible client payloads.

Non-goals:

- No account system.
- No change to the ranking truth: ranking remains `totalTokens`.
- No upload of prompts, assistant responses, source code, full transcripts, real absolute paths, Cursor session tokens, or identity private keys.
- No forced upgrade for clients that are still within the supported compatibility window.
- No native installer requirement in this phase unless the selected updater mechanism requires one.

## 2. Version Model

0.3 separates three version concepts:

| Concept | Owner | Purpose |
| --- | --- | --- |
| App version | Desktop / CLI package | User-visible release version, for example `0.3.0`. |
| Client protocol version | Desktop / CLI upload client | Declares the request contract used by device registration, health, and usage upload. |
| Provider/parser version | Provider implementation | Explains how local usage was parsed; remains per provider in usage facts. |

Product rule:

- App version tells users what they installed.
- Client protocol version tells the server whether the request is compatible.
- Provider/parser version remains data lineage, not product upgrade state.

## 3. API Compatibility Baseline

The active upload route remains:

```text
POST /api/usage/daily-batch
```

0.3 adds compatibility metadata to client-facing requests and responses.

Client requests should include:

```text
clientAppVersion
clientProtocolVersion
clientPlatform
clientBuild
```

Server responses should expose:

```text
serverVersion
serverProtocolVersion
supportedClientProtocol
latestClientVersion
compatibility
```

Compatibility outcomes:

| Outcome | Meaning | Product behavior |
| --- | --- | --- |
| compatible | Client can upload normally | No blocking UI. |
| upgrade_available | Client can upload, but newer version exists | Non-blocking update notice. |
| upgrade_recommended | Client can upload, but is near compatibility boundary | Visible warning with update action. |
| unsupported_client | Server rejects upload because protocol is too old | Block sync, keep local queue, show update action. |
| unsupported_server | Client does not understand the server contract | Block sync, keep local queue, show server/API warning. |

Failed compatibility checks must not discard local usage or identity data.

## 4. Client Version Visibility

Desktop Settings / System should show:

- App version.
- Build platform and architecture.
- API target.
- Server version when reachable.
- Compatibility status.
- Latest available client version when known.
- Last update check time.

CLI should expose the same information through health/status output.

## 5. Self-Upgrade Baseline

0.3 introduces a release manifest checked by the client.

Manifest minimum fields:

```text
version
channel
generatedAt
protocol
platforms
sha256
releaseNotesUrl
mandatory
```

Product rules:

- The client checks for updates explicitly from Settings / System and also checks in the background every 6 hours when background refresh and API target are configured.
- Update availability is advisory unless the server marks the current client protocol unsupported.
- Downloaded artifacts must be checksum-verified before launch or handoff.
- 0.3 uses download + checksum verify + explicit handoff instead of replacing a running app.
- The update path does not modify identity, local config, provider roots, Cursor tokens, aliases, usage cache, or upload queue.
- If download or checksum verification fails, the current client remains usable when its protocol is still supported.

0.3 should support at least macOS arm64, macOS Intel x64, and Windows x64 artifacts because those are the current distribution targets.

## 6. Verification Baseline

Minimum verification before freezing 0.3:

```bash
node --check src/desktop/renderer.js
node --check src/desktop/main.cjs
npm test
npm run desktop:smoke
npm run package:all
```

Additional 0.3 verification:

- Old client without version metadata receives a deterministic compatibility result.
- Current client uploads with version metadata and remains accepted.
- Unsupported protocol upload is rejected without deleting the upload queue.
- Desktop displays app/server/latest version states.
- Update manifest parsing rejects missing checksum or unsupported platform.
- macOS arm64, macOS Intel x64, and Windows x64 packages expose the correct app version.
- Self-upgrade dry run verifies artifact checksum and preserves local config paths.

## 7. Confirmed Decisions

- Apply mechanism: 0.3 uses check/download/verify plus explicit user handoff. It does not replace a running app.
- Manifest scope: CLI and Desktop share one manifest; platform-specific artifacts live under `platforms`.
- Update manifest transport: Aliyun OSS public-read resources. The concrete endpoint, bucket, prefix, public base URL, and manifest path must be injected through env instead of hard-coded.
- Manifest signing: deferred for the open-source phase. Artifact integrity is verified with sha256 checksum; OSS write permission and release process protect manifest publication.
